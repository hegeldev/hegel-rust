# Code map: test-runner

> Research notes compiled 2026-09-02 at commit a0185a65 (branch base, == main at the time).
> References are `path:line` at that commit. Part of the nondeterminism design notes; see `../design.md`.

SUMMARY: The engine test runner (hegel-c/src/native/test_runner.rs) is a single async driver, Engine::run, that owns four phases in sequence — database reuse replay, generation (with targeting and span mutation folded in), per-origin shrinking, and database reconciliation — and returns a TestRunResult of one Failure per distinct panic origin; the frontend, not the engine, performs the final replay of each reproduce blob. Determinism is assumed everywhere via a lossless choice tree that records every execution and serves replays without re-running the body; violations surface as two distinct run-aborting errors (RunError::NonDeterministic for a choice-kind change at the same prefix, RunError::Flaky for a status/origin change on identical choices) plus a frontend-side flaky panic when a blob replay stops failing. The one sanctioned escape hatch is a sticky Engine::nondeterministic flag, flipped when a test case creates a state machine with max_concurrency > 1, which disables tree recording, novel-prefix generation, targeting, span mutation, shrinking, database persistence/reuse, and reproduce blobs, reporting failures from the discovering execution via a frontend-side stash.

## Run lifecycle: phase sequence and transitions
explore() -> run_main() -> Engine::run drives everything in one function. (1) Reuse phase (gated on Phase::Reuse + db + key): fetches primary-key entries plus a shortlex-sorted sample of secondary entries, replays each via test_function; non-interesting entries are deleted from the db; stops early at first interesting when !report_multiple_failures. (2) Generation (gated on Phase::Generate && !found_in_reuse && !test_is_trivial): first a for_simplest probe with the LargeInitialTestCase health check, then batches of RANDOM_GENERATION_BATCH=10 cases with novel prefixes from generate_novel_prefix; loop conditions are valid_test_cases < settings.test_cases, within_invalid_budget (Hypothesis's _invalid_thresholds: (458,100) at r=0.01,c=0.99), !tree_root.is_exhausted, and should_generate_more (post-bug window min(first_bug+1000, last_bug*2), MIN_TEST_CALLS=10 floor, 10s wall cap after first bug; returns false immediately post-bug when shrinking disabled or !report_multiple). Targeting (Phase::Target) fires inside the loop via TargetingSchedule/Optimiser; span mutation runs on valid cases after 10 valid or once a bug exists. (3) Shrink phase runs iff !interesting.is_empty() && !replay_aligned && Phase::Shrink && !nondeterministic; replay_aligned means the reuse replay realized exactly the stored primary choices, so shrinking is skipped as already-shrunk. (4) End-of-run db reconciliation moves displaced primary entries to secondary and saves the shrunk set. Final replay is NOT in the engine: every case explore runs is non-final; the caller replays blobs (module doc lines 1-16, 108-116).

## test_function / record_run: every execution feeds the lossless choice tree
Engine::test_function executes one case through the CaseExchange (execute() at 1146-1172 reads nodes/spans/span_events/targets/events/outcome off NativeDataSource) and then record_run records it into the data tree via record_tree_full — nodes, span events, status, origin, target observations — making the tree lossless, so simulate_full can serve any recorded path (any status, interesting included) without re-running the body. cached_test_function (Hypothesis's cached_test_function) is the single replay chokepoint for span mutation and shrinking: tree hit -> served without execution; miss -> test_function. There is no separate result cache; the tree is the sole source of truth. record_run also updates counters (calls, valid/invalid/overrun), test_is_trivial (empty concluding case), targeting records, statistics, first/last_bug markers, incremental Persister::record (interesting cases saved to db at discovery and every shortlex improvement, so Ctrl-C mid-shrink keeps the failure), and update_interesting.

## Re-execution site 1: choice-tree mismatch check (RunError::NonDeterministic)
record_tree_full compares only the CHOICE KIND at each position against what earlier runs recorded at the same prefix (values just branch the trie; a changed kind returns the message 'Your data generation is non-deterministic: at the same choice position with the same prefix, the choice kind changed from {:?} to {:?}. This usually means a generator depends on global mutable state.'). test_function returns this as Option<String> mismatch alongside the RunResult. The mismatch is CHECKED (Err(RunError::NonDeterministic(msg)) aborts the whole run) at: the reuse replay loop (247), the for_simplest probe (303-304), the generation loop (372-373), and the shrink verify (538-539). It is IGNORED at: the pre-shrink secondary-db replay (509 discards the tuple), cached_test_function (1222 binds _mismatch — so span-mutation probes and all shrink probes never check it), and the targeting optimiser (targeting.rs:133 binds _mismatch). Note the tree never compares conclusions: re-recording the same full path with a different status silently overwrites leaf.conclusion (data_tree.rs:307-315). Also, replaying a prescribed prefix value that no longer fits a draw does NOT error at draw time — resolve_choice puns it to simplest()/unit() (state.rs:2442-2492); the kind change is only caught later by the tree at record time. Clone subtrees deliberately do NOT report nondeterminism on contradiction — prediction is disabled instead (clone_subtree_disabled, data_tree.rs:148-155, 335-361), because a cloned stream may legitimately depend on other streams.

## Re-execution site 2: shrink verify + shrink probes (RunError::Flaky)
Before shrinking each origin, Engine::run re-executes the stored counterexample exactly (NativeTestCase::for_choices with the recorded nodes, via test_function at 536-537 — note this bypasses the tree cache, so it genuinely re-runs unless the record already served it). It then compares: verify.status != Status::Interesting || verify.origin.as_deref() != Some(origin) -> Err(RunError::Flaky(flaky_diagnostic())) which ABORTS the entire run (no failures reported). flaky_diagnostic() (762-769): 'Flaky test detected: Your test produced different outcomes when run with the same generated data...'. What is compared: status and interesting-origin string only — not the realized choice sequence (choice-sequence divergence is the tree's job, checked one line earlier via the mismatch). During shrinking itself, EngineShrinkProbe routes every candidate through cached_test_function and reports matches = (status == Interesting && origin == target_origin) (1258-1260); a non-matching probe is simply an unsuccessful shrink, never a flakiness error — but a probe whose origin is NEW lands in the interesting map via update_interesting and gets its own shrink round (the loop at 521-569 iterates until all origins, including ones discovered mid-shrink, are shrunk; shrunk_origins tracks completion). Shrinking has a wall-clock budget MAX_SHRINKING_SECONDS=300 (core/mod.rs:84), surfaced as ShrinkHalt::Stop, absorbed by absorb_stop, with slow_shrink_warning printed (571-573, 788-795).

## Re-execution site 3: frontend final replay flaky check
The engine never does a final replay. run_lifecycle::drive pumps non-final cases, then reads hegel_run_result; on HEGEL_RUN_STATUS_FAILED it replays each failure's reproduce blob via CTestCase::from_blob + run_test_case(is_final=true) and panics with FLAKY_DIAGNOSTIC (same wording as the engine's, defined separately at run_lifecycle.rs:483-487) if the replay is not Interesting — an abort of the test with the flaky message, after the engine considered the run failed. drive_blob_replay (reproduce_failure attribute) similarly panics 'the supplied failure blob no longer reproduces a failure' when the replay passes (731-735). The blob replay data source is a bare for_choices replay with no rng and no template (embed.rs:98); a draw past its end surfaces as StopTest/overrun.

## The sticky nondeterministic flag (concurrent stateful testing) and what it disables
Engine.nondeterministic (field doc at 990-998) is flipped by the first executed case that created a state machine with max_concurrency > 1: NativeDataSource::new_state_machine calls family.set_concurrent_machine() and, while family.reject_concurrent_machine() is true (set to !engine.nondeterministic per case at test_runner.rs:1061), rejects the creation as EngineError::AssumeViolation — so the flipping case itself is discarded as Invalid (frontend classifies DataSourceError::Assume as TestCaseResult::Invalid, run_lifecycle.rs:309-311). After the case, test_function sees family.concurrent_machine() and sets nondeterministic=true, printing concurrent_machine_notice() once (1065-1070, 777-781). Every subsequent NativeTestCase is stamped via ntc.set_nondeterministic() BEFORE it runs (1056-1058; state.rs:1788-1795), exposed as hegel_test_case_is_nondeterministic (hegel-c/src/lib.rs:1524-1544) so the frontend knows at case start to capture output/diagnostics at discovery (run_lifecycle.rs:288). While set, the engine skips: tree recording and the mismatch check (record_run 1084-1096), test_is_trivial (1099), novel-prefix generation (357-361, pure random instead), reuse continuation (273-276), targeting (426), span mutation (439), shrink phase entirely (473) and post-bug extra generation (should_generate_more gets shrink_enabled=false at 329/344, so generation stops at first bug), db persistence (1120-1122) and reconciliation (588), and reproduce blobs (638-643: reproduce_blob=None).

## Failure deduplication and multi-failure handling
Identity = the origin string, produced frontend-side as format!("Panic at {location}") from the panic hook's file:line:col capture (run_lifecycle.rs:345-347; '<unknown>' when the hook saw nothing, notably panics propagated from unjoined threads via resume_unwind, run_lifecycle.rs:200-217). It crosses the ABI through mark_complete and lands in Engine.interesting: HashMap<String, Vec<ChoiceNode>> (one shrunk counterexample per origin, test_runner.rs:966-970). update_interesting (864-879) inserts on first sighting and replaces only when the new nodes' sort_key (shortlex) is smaller. Each origin is shrunk independently, in sorted-origin order, with the shrink loop re-scanning for origins discovered mid-shrink (521-569). Report assembly: origins_sorted sorted by sort_key descending (617-619); if !settings.report_multiple_failures only the last (smallest) entry survives (621-626). Multi-bug discovery is driven by should_generate_more's post-first-bug window (only when shrinking is enabled and report_multiple is on).

## Aggregate result assembly and how the frontend reads it
Engine::run ends by mapping origins_sorted into Vec<Failure> {origin, reproduce_blob: Option<String>} — blob is base64 encode_failure(choices) unless nondeterministic — inside TestRunResult {failures, nondeterministic} (634-653). RunError aborts instead: Err propagates out of the engine future. In libhegel's C ABI, hegel_next_test_case polls the engine future; Poll::Ready(Ok) -> HegelRunResult::from(TestRunResult), Poll::Ready(Err) -> HegelRunResult::from_error(msg) (lib.rs:1300-1323), so ALL RunError variants (HealthCheck/Flaky/NonDeterministic/UsageError/Internal) collapse to one error string read via hegel_run_result_error; status mapping (lib.rs:713-723): error -> HEGEL_RUN_STATUS_ERROR, no failures -> PASSED, failures+nondeterministic -> FAILED_NONDETERMINISTIC, else FAILED. Frontend RunHandle::result wraps hegel_run_result (src/ffi.rs:321-330, accessors 1414-1478). drive() dispatch (run_lifecycle.rs:576-644): ERROR -> panic!(engine message); FAILED_NONDETERMINISTIC -> print the NondetStash captured at discovery (buffered draw/note lines + rendered diagnostic + caught panic payload, stashed for every frontend-interesting non-final case at 566-573; struct doc 451-477 explains a stash can 'lose' to an engine-side family conclusion, in which case a passing verdict discards it) and resume_unwind the stashed payload; FAILED -> replay each blob as final, print diagnostic + reproducer line, re-raise the last payload (or a count message for multiple bugs). Mode::SingleTestCase bypasses explore entirely: run_single_case offers one random case (state-machine steps unbounded, state.rs:1492) and returns its failure with nondeterministic hardwired false (test_runner.rs:138-152, embed.rs:64-71) — a failing single case reports FAILED even with a concurrent machine (lib.rs:214-218).

## Reuse-phase determinism assumptions (replay_aligned and db hygiene)
The reuse phase assumes a stored choice sequence replays to the same outcome: entries that replay non-interesting are DELETED from primary and secondary keys (267-272) — a nondeterministic test would silently lose its persisted counterexample on an unlucky replay. replay_aligned (skip-shrink optimization) requires the interesting replay to be from the primary key AND to realize exactly the stored choices, node count and values compared elementwise (249-263). If the run flipped nondeterministic during reuse, the loop breaks and replay_aligned is cleared (273-276). The pre-shrink pass also replays remaining secondary entries shortlex-below the current worst counterexample to seed the shrinker's tree, deleting each (484-515).
refs: hegel-c/src/native/test_runner.rs:198-283, hegel-c/src/native/test_runner.rs:484-515

## RunError type inventory
RunError (hegel-c/src/backend.rs:358-376): HealthCheck(String), Flaky(String) — 'test produced different outcomes when run on identical data', NonDeterministic(String) — 'data generation diverged between runs of the same choice sequence', UsageError(String) — driving-contract violations (e.g. NativeDataSource::take_outcome when a case was never concluded, data_source.rs:95), Internal(InternalError). Display collapses all to the message. The two nondeterminism-adjacent variants are thus distinguished by CAUSE: Flaky = same choices, different verdict; NonDeterministic = same prefix, different draw structure.
refs: hegel-c/src/backend.rs:358-398, hegel-c/src/native/data_source.rs:95

RELEVANCE: The runner assumes full determinism at every layer and the assumption is load-bearing in five places: (1) the lossless choice tree doubles as generation-dedup (novel prefixes), replay cache (simulate_full serves recorded paths without execution — so a nondeterministic test would be 'replayed' from stale recorded outcomes silently), and the nondeterminism detector itself; (2) the shrink verify demands exact status+origin reproduction and aborts the ENTIRE run (RunError::Flaky) on mismatch rather than degrading — a flaky test loses its bug report entirely, and the tree mismatch (RunError::NonDeterministic) does the same; both surface as HEGEL_RUN_STATUS_ERROR with no failures; (3) the database assumes replay fidelity: entries that don't reproduce are deleted, and replay_aligned skips shrinking on exact choice-sequence equality; (4) failure identity is a panic-site string, already lossy for concurrency (panics from unjoined threads all collapse to 'Panic at <unknown>', run_lifecycle.rs:200-217); (5) the final report is produced by the frontend RE-RUNNING each blob, so a failure that doesn't replay panics as flaky even after the engine declared the run failed. The existing escape hatch — the sticky Engine::nondeterministic flag — is all-or-nothing and engine-initiated (flipped only by concurrent state machines, mid-run, discarding the flipping case): it turns off the tree, shrinking, targeting, span mutation, persistence, and blobs wholesale, stops generation at the first bug, and moves failure reporting to a frontend stash captured at discovery (which can silently lose to an engine-side family conclusion and relies on hegel_test_case_is_nondeterministic being stamped before the case runs). Notably inconsistent seams a design must reconcile: the tree-mismatch check is enforced only on generation/reuse/verify executions but ignored on shrink probes, span mutation, targeting, and the secondary-db replay; the tree silently overwrites a conclusion when the same path re-records with a different status; and mode is currently binary with no per-test declaration, no partial degradation (e.g. shrink-with-retries), and no statistical treatment of probabilistic failures.
