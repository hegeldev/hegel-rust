# Adversarial review of design sketch v0: representation

> Compiled 2026-09-02 against commit a0185a65. The sketch under review is `sketch-v0.md`.
> These findings drove the v0 -> v1 changes recorded in `../design.md` and `../decisions.md`;
> unresolved ones appear there under "Known risks" and "Deferred decisions".

VERDICT: The ND-node mechanism as sketched contradicts several load-bearing behaviors of the actual code: draw-time validation is far too weak to anchor branch points (booleans validate unconditionally, integers only need containment, fresh-id/from-set repair instead of rejecting), punning is a deliberate shrinking mechanism the sketch would break by replacing it with widening, and the data tree's conclusion-at-leaf / forced-once / value-keyed-children assumptions all become live corruption sources once ND runs are recorded. Worst, the top workload (concurrent stateful) diverges almost entirely inside clone streams, where the codebase's own precedent (clone_subtree_disabled) already concedes that per-position prediction is hopeless — so ND nodes either fire constantly on benign schedule noise there or must be scoped out, leaving the mechanism to serve only the third-priority workload. The tree restoration (area 4) is feasible but needs three unstated semantic decisions (interior conclusions, forced-flag drift, per-kind child keys); the ND-node choice-sequence representation (area 3) needs a fundamental rethink of where divergence is detected and what the canonical stored artifact is.

## [HIGH] Kind-compatible structural divergence is invisible to both widening triggers — the ND node has nowhere to land
The sketch's widening trigger is 'a recorded value/kind no longer fits the requested draw', but the two detection mechanisms both miss the dominant divergence class. At the draw: ChoiceKind::resolve accepts any bool for a Boolean regardless of p (choices.rs:1228-1230), any in-range integer, and draw_from_set's from_prefix accepts any in-window integer including non-members (repaired after acceptance, state.rs:2226-2248), while draw_fresh_id repairs out-of-window/duplicate ids silently (state.rs:2153-2186) and forced draws never consult the prefix at all (weighted forced path, state.rs:2405-2407). At record time: record_tree_full only detects a changed kind at an identical realized-value path (data_tree.rs:268-276). So a divergence that shifts structure without changing kinds — e.g. a collection reject() that fires in one timeline but not another (many_reject/force_stop, draws/mod.rs:399-415), shifting every subsequent draw by one element of identical kinds — replays 'successfully' with stored values consumed at wrong semantic positions, produces no misfit, no tree mismatch, only a different verdict. The sketch classifies only same-realized-sequence-different-verdict as outcome-ND; this is different-structure-same-kinds, a third class it cannot represent: there is no observable branch point, so no ND node can be placed and the cross-timeline grafting pass (point 5) has no node to graft at. The design must state that ND nodes capture only the kind-visible minority of divergences, or add a different anchor signal (e.g. span-structure/draw-count comparison between timelines).
refs: hegel-c/src/native/core/choices.rs:1223-1242, hegel-c/src/native/core/state.rs:2153-2263, hegel-c/src/native/core/state.rs:2389-2418, hegel-c/src/native/draws/mod.rs:373-415, hegel-c/src/native/data_tree.rs:261-292

## [HIGH] For the #1 workload (concurrent stateful) misfits are dominated by benign schedule noise, so widening fires on nearly every execution
In worker streams, draw_fresh_id/draw_from_set windows are family-wide and schedule-dependent — the doc admits 'racing clone streams can skew each other's windows' (state.rs:2146-2152) — so on replay under a different schedule a recorded id routinely falls out of window or is already used, a misfit/repair per pool draw. next_rule's p_continue depends on steps_rejected (state_machine.rs:367-376), which depends on assume failures against shared model state, and retry_pending forces p=1.0 (a forced node) — so kinds and forced flags drift per schedule even when nothing is wrong. The existing design shunts exactly this noise into clone nodes where kind drift is tolerated and prediction is disabled on contradiction (clone_subtree_disabled, data_tree.rs:148-159, record_clone_record data_tree.rs:338-349) rather than reported. ND-node widening inside worker streams would therefore create branches at pool/continue draws on nearly every run of a pool-using machine, saturating any branch cap immediately with meaningless alternatives. The consistent resolution is the one the tree already made — no ND nodes inside clone streams — but then workloads #1 and #2 (concurrent stateful, clone-based concurrency) get no benefit from the ND-node mechanism at all; only single-stream external-randomness tests do. The design should say this explicitly and justify the mechanism's cost against the workload it actually serves.
refs: hegel-c/src/native/core/state.rs:2127-2263, hegel-c/src/native/core/state_machine.rs:350-413, hegel-c/src/native/data_tree.rs:148-159, hegel-c/src/native/data_tree.rs:338-349

## [HIGH] Branch selection by 'first branch whose head satisfies the current constraint' is vacuous for structure-encoding draws
Booleans satisfy any Boolean draw (choices.rs:1228-1230) and most integer draws' constraints contain all recorded heads, so the rule degenerates to 'always pick the first (failing) branch' — the other branches are dead weight at replay and never steer anything. The obvious stronger discriminator, bit-exact kind matching against the branch's stored nodes, fails the other way: BooleanChoice equality is bit-exact on p (choices.rs:125-128) and p is schedule-noisy in exactly the ND workloads (p_continue depends on completed-rule counts), and IntegerChoice windows drift with fresh-id registries — so exact-kind matching would spuriously reject the correct branch and fall through to fresh random generation. Neither semantics does the job the sketch assigns; branch selection needs an actual design (tolerant kind matching, or lookahead over the suffix's kinds) and an account of what a wrong selection costs (grafting the failing suffix onto the wrong timeline = random values = failure probability collapse, violating the 'shrinking must not lower probability' constraint from the replay side).
refs: hegel-c/src/native/core/choices.rs:125-128, hegel-c/src/native/core/choices.rs:1223-1242, hegel-c/src/native/core/state_machine.rs:362-380

## [HIGH] Misfit-site widening misattributes the branch point, and position anchoring silently breaks after the first forced/repaired draw
When a misfit does occur, the true divergence usually began earlier at a position where the recorded value coincidentally satisfied the new constraint (Integer 3 fits both 0..10 and 0..100; resolve validates containment only, choices.rs:1225-1227; boolean p drift is invisible to resolve but is kind drift to the tree). The tree's kind check fires earlier and more precisely, but mapping its realized-path position back to a stored-sequence index is valid only while realized == stored values verbatim — and that invariant breaks at the first forced draw whose recomputed value differs (retry_pending forced continue depends on ND model state, state_machine.rs:370-376; budget-forced stops in next_group, state_machine.rs:300-308), at the first fresh-id repair, and at the first pun. resolve_choice records nothing about whether a value came verbatim from the prefix versus punned (state.rs:2450-2492), so the widening machinery cannot currently know whether its stored-position anchor is still valid. The design needs an explicit runtime 'replay still verbatim' watermark and a rule that widening stops (or degrades to whole-suffix branches) past it; the sketch does not mention this at all.
refs: hegel-c/src/native/core/state.rs:2450-2492, hegel-c/src/native/data_tree.rs:268-276, hegel-c/src/native/core/state_machine.rs:290-386

## [HIGH] Data tree: conclusion-vs-continuation contradiction is unhandled and becomes the normal case under ND
record_tree_full never inspects an interior node's conclusion during the walk (data_tree.rs:261-292) and stores conclusions only at the current run's leaf (307-315); check_exhausted marks any concluded node exhausted (191-194); simulate_full returns a conclusion before consuming further choices (610-619). A test that concludes at depth 5 in one run and continues to depth 8 in another (early ND panic, ND assume) therefore silently produces: a node holding both a conclusion and children, stale conclusions served by cached_test_function for the longer path (test_runner.rs:1202-1215), and a prematurely-exhausted subtree that novel-prefix generation refuses to explore. 'Conclusions become outcome distributions' addresses only the verdict multiplicity, not the structure: the design must define what a node with both a conclusion-distribution and children means to simulate_full (stop or continue?), to check_exhausted (a 'continued past this node' count is needed), and to generate_novel_prefix — otherwise restoring the tree for ND runs actively corrupts generation.
refs: hegel-c/src/native/data_tree.rs:187-209, hegel-c/src/native/data_tree.rs:261-315, hegel-c/src/native/data_tree.rs:607-619, hegel-c/src/native/test_runner.rs:1196-1224

## [MEDIUM] Forced-flag drift corrupts the restored tree: premature exhaustion and an arbitrary-child unwrap in novel-prefix generation
DataTreeNode.forced is fixed on first visit and never re-validated (data_tree.rs:277-281, the `_ => {}` arm ignores a changed forced flag when kinds match). Under ND, forcedness flips at the same position across runs (budget-forced next_group stops, retry_pending forced continues, many_more's min/max forcing when counts diverge). A node first recorded forced then visited unforced with a different value accumulates multiple children while check_exhausted's forced arm declares it complete at explored>=1 (data_tree.rs:196-203) — premature exhaustion that kills exploration of a live subtree — and generate_novel_prefix's forced path takes children.iter().next() (HashMap iteration order, i.e. a nondeterministically-chosen child) and debug-asserts the child is non-exhausted (data_tree.rs:489-497), an assert that can now fire. Widened/ND tree nodes need forced to become per-branch state, and the deterministic-node forced fast path needs a mismatch rule.
refs: hegel-c/src/native/data_tree.rs:120-128, hegel-c/src/native/data_tree.rs:196-203, hegel-c/src/native/data_tree.rs:277-281, hegel-c/src/native/data_tree.rs:488-497

## [MEDIUM] Two irreconcilable incumbent representations: everything engine-side is single-execution realized nodes, and every accepted shrink invalidates all folded branches
The shrinker's incumbent, update_interesting, Persister, end-of-run reconciliation, and final Failure/blob all operate on the realized Vec<ChoiceNode> of one execution (test_runner.rs:864-937, 588-649; shrinker/mod.rs:312-348) — realized sequences never contain ND nodes, since a single run takes one timeline. The merged multi-branch artifact exists only as the proposed DB value / blob. But branch suffixes are only meaningful relative to a fixed trunk, and accept_improvement replaces the trunk on every accepted shrink, invalidating every previously folded branch; unless fold-in restarts after shrinking finishes, the final stored artifact degenerates to one branch and the ND node machinery contributes nothing to the reproducer. Consequently the proposed NodesSortKey extension ('failing branch's key first, then branch count') has no comparison site: consider() and update_interesting only ever compare realized nodes, and DB reconciliation compares serialized bytes (test_runner.rs:588-608) — merged artifacts whose bytes change on every fold-in would churn the primary corpus and bloat .secondary with stale merged variants. The design must name the canonical per-origin object (realized incumbent + separate branch store?), when folding happens relative to shrinking, and which comparisons — if any — ever see an ND node.
refs: hegel-c/src/native/test_runner.rs:864-937, hegel-c/src/native/test_runner.rs:588-649, hegel-c/src/native/shrinker/mod.rs:312-348, hegel-c/src/native/core/choices.rs:1834-1855

## [MEDIUM] extend=0 replay semantics bias every ND replay toward overrun: bare replays cannot follow a diverged, longer timeline
ShrinkRun::Full replays via cached_test_function(choices, nodes, 0) (test_runner.rs:1246-1251), i.e. for_choices with max_size capped at choices.len() (state.rs:1722-1728, for_choices at 1727), so any divergence that lengthens the path overruns as EarlyStop and scores 'not interesting' — and a bare replay that diverges before a clone position hands the child prefix.len()==0 with no RNG (clone_stream child_max_size, state.rs:1830-1834), overrunning the whole family on the child's first draw. For retry-shaped workloads divergence usually lengthens paths, so the sketch's cheap single-run predicate systematically undercounts failure probability, in tension with the 'shrinking must not lower failure probability' constraint. The same applies to the frontend's final blob replay (embed.rs data_source_for_blob → for_choices with no RNG, embed.rs:87-103) and to shrink-phase secondary-corpus replays (test_runner.rs:507-509). ND replays need a continuation budget everywhere, which changes overrun accounting, the verify semantics, and the health-check counters — a decision, not plumbing.
refs: hegel-c/src/native/test_runner.rs:1239-1263, hegel-c/src/native/core/state.rs:1722-1728, hegel-c/src/native/core/state.rs:1810-1857, hegel-c/src/embed.rs:87-103

## [MEDIUM] The restored tree's conclusion cache must be bypassed in ND mode, at which point outcome distributions have no consumer
cached_test_function serves any tree-recorded path without executing (test_runner.rs:1202-1215), so the multi-run interestingness predicate and the shrink single-run predicate would receive the first recorded verdict back N times, masking exactly the probability being measured. If ND mode always executes instead (necessary), the tree's per-path outcome distributions are never read for decisions: candidate-level failure-rate stats already need the separate proposed-candidate-keyed store the sketch posits (the tree is keyed by realized paths, which vary per run of the same candidate), and reporting reads the run results directly. The tree's ND-mode value then reduces to novel-prefix generation plus divergence detection; specifying, storing and maintaining {status,origin}->count distributions in it is dead weight. Either find a real consumer or drop distributions from the design.
refs: hegel-c/src/native/test_runner.rs:1196-1224, hegel-c/src/native/data_tree.rs:597-671

## [MEDIUM] Tree widening needs (kind,value) child keys, and record_tree_full's mismatch early-return leaves the tree half-updated under Quiet
children are keyed by ChoiceValueKey — value only (data_tree.rs:37-45, 286-291). Widening a node to hold multiple kinds means two timelines drawing the same value under different constraints (Integer 3 under 0..10 vs 0..100 — genuinely different branches with different continuations) collide into one child subtree, splicing distinct continuations together and cascading spurious kind-mismatches (hence spurious further widening) deeper down. The sketch's parenthetical 'possibly per kind' must be a definite: ND tree nodes need per-(kind,value) children, and max_children/exhaustion accounting (max_children_saturating is a function of one kind, choices.rs:1263-1285) needs an ND-node rule beyond 'never exhausted' for its ordinary siblings. Separately, record_tree_full returns the mismatch before recording the rest of the path, before writing span events, and before the bottom-up check_exhausted pass (data_tree.rs:269-276 vs 294-331) — harmless today because the run aborts, but under Quiet flip-and-continue the tree is left with inserted children and stale exhaustion flags; widening must either complete the walk transactionally or re-record the run after widening.
refs: hegel-c/src/native/data_tree.rs:37-58, hegel-c/src/native/data_tree.rs:261-333, hegel-c/src/native/core/choices.rs:1263-1285

## [MEDIUM] Flip-site list misses the shrink phase, and the no-stamping claim contradicts the frontend's output gating
Shrinker/span-mutation replays route through cached_test_function, which discards the tree mismatch (test_runner.rs:1222, `_mismatch`), so ND that first manifests under shrink-mutated inputs reaches none of the sketch's flip sites (reuse/probe/generation/verify) — it surfaces later as RunError::Flaky at verify (test_runner.rs:541-545) or the final-replay panic, after shrinking has already run against a tree serving stale conclusions. And the claim that unified reporting removes the need to stamp cases before they start ignores run_lifecycle::run_test_case: should_emit is false for ordinary non-final cases (run_lifecycle.rs:286-302), so the discovering case in a not-yet-ND run renders no draw/note lines. When the final up-to-N replays all pass, the sketch's caveated per-origin discovery capture has no rendered values to show for exactly the transition case. Options are all costly: render every case's output always, re-run the discovering case (reintroducing the sacrifice), or accept a value-less caveated report; the sketch must pick one.
refs: hegel-c/src/native/test_runner.rs:1216-1224, hegel-c/src/native/test_runner.rs:533-545, src/run_lifecycle.rs:273-305

## [LOW] Serialization and identity details: ND-in-clone needs CloneRecord equality semantics; reuse still wipes a flaky corpus before the ND bit exists
A new ND choice tag must recurse with the MAX_CLONE_DEPTH-style cap deserialize_choice_list already enforces (database.rs:330-336), and ND values inside clone child sequences require extending CloneRecord's value-based Eq/Hash (choices.rs:906-918) with a defined branch-set equality (order? count?), since the data tree keys clone children by whole records — otherwise ND-bearing records can't round-trip or be looked up. Bootstrapping order: reuse deletes any entry that replays non-interesting from both corpora immediately (test_runner.rs:267-272); the sketch's 'replay each stored entry up to N' only applies once the per-test ND bit exists, but a first-discovery 10%-flaky bug has no bit yet, so its corpus entry is still deleted on the first lucky replay of the next run — the persisted ND bit must be written at first Interesting sighting (alongside Persister.record), not at flip time. Also note old binaries delete new-format entries as undecodable (test_runner.rs:236-241) — acceptable, but state it. Finally, per-branch suffix storage should be values-only like clone serialization (database.rs:215-217): trunk spans straddling the ND position have branch-dependent ends, so 'nodes+spans like RealizedStream' overcommits — spans must be rebuilt (or stored as events), never stored as finished per-trunk Span lists.

# IMPROVEMENTS
## Scope widening strictly to verbatim-replay contexts; keep punning for shrinker candidates
resolve_choice's pun-to-simplest/unit is load-bearing for shrinking: passes deliberately propose misfitting prefixes (deletions, one_of switches) and rely on punning to converge (state.rs:2442-2492; shrinker consider() adopts realized post-pun nodes). If ND replay replaced puns with widen-plus-fresh-random during shrink candidate runs, candidates would stop being a function of the proposed prefix. Widen only during verify/DB-reuse/blob replays of a known timeline (where the prefix is a previously-realized full sequence), never for shrinker-generated prefixes — and say so in the design.

## Consider K stored timelines per origin instead of a merged branch-tree artifact
Most of the representational cost (new ChoiceValue variant everywhere, CloneRecord equality, sort-key extension, serialization recursion, branch caps, trunk invalidation on every shrink) disappears if the DB/blob simply stores a small set of complete realized failing sequences per origin (the existing multi-value DB and .secondary sub-corpus conventions already support this shape) and replay tries each with a continuation budget. Per-value shared-trunk suffix trees only pay off when trunks are long-lived, which shrinking actively prevents; measure the sharing win before committing to the ND-node encoding.

## Add a structural divergence checksum instead of relying on kind/value misfits
Since kinds and values cannot see the dominant divergence class, compare cheap structure between the recording and the replay: draw count, span open/close event sequence (span_events are already recorded per stream, state.rs:1591-1594), or per-position label of the engine-emitted draw spans. A first-structural-difference position is a far better ND-node anchor than the first constraint violation, and it works for boolean-encoded control flow.

## Define the ND-mode tree as detection+novel-prefix only
Make simulate_full/cached_test_function unconditionally execute when the run is ND (never serve conclusions), drop conclusion distributions, treat widened nodes as never-exhausted, and add a 'continued past' marker so interior conclusions stop implying exhaustion. This keeps the restore-the-data-tree goal (novel prefixes for ND runs) at a fraction of the specified complexity.

## Write the persisted ND bit at first-failure time, not flip time
Persister.record already runs on every Interesting result (test_runner.rs:1113-1124); recording 'this origin was observed at least once' plus a replay-count-before-delete policy for reuse protects a flaky corpus from the first lucky replay even before any divergence has been observed, closing the bootstrapping gap without needing detection to have fired.
