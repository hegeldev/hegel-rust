# Adversarial review of design sketch v0: lifecycle

> Compiled 2026-09-02 against commit a0185a65. The sketch under review is `sketch-v0.md`.
> These findings drove the v0 -> v1 changes recorded in `../design.md` and `../decisions.md`;
> unresolved ones appear there under "Known risks" and "Deferred decisions".

VERDICT: Areas 1, 2 and 6 build on real seams (Failure.reproduce_blob is already Option, sub_key exists, FAILED_NONDETERMINISTIC already crosses the ABI, the stash gives a capture precedent), but the sketch has three load-bearing errors: N=10 replay-until-failure misses the stated p>=0.1 target ~35% of the time, so the "caveated fallback" is a common path, not an edge case — and that fallback is far more degraded than the sketch assumes because every capture decision (document emit, diagnostic render, backtrace) is made before the test body runs, which is exactly what the "no stamp needed" claim breaks; DB-reuse divergence is not evidence of nondeterminism (it is overwhelmingly evidence of a code change) and persisting an ND flag from it would mis-stamp deterministic tests routinely; and the persistence mechanism is inert in CI where the database is disabled by default. The confirmation machinery also needs explicit carve-outs from run accounting, the tree cache, and event statistics, none of which the sketch states.

## [HIGH] N=10 confirmation misses the design's own p>=0.1 target a third of the time
P(reproduce in 10 tries at p=0.1) = 1-0.9^10 = 0.65, so for a bug at exactly the stated target rate the 'unified replay-until-failure' report falls back to the caveated discovery capture ~35% of the time; 95% coverage at p=0.1 needs ~29 replays, each a full execution of the user's test at report time (worst for the top workload: concurrent stateful, 50 steps x workers per replay). The fallback path is therefore the common path at the low end of the target range, and its quality (next finding) is much worse than the sketch assumes. Additionally the design double-pays: engine-side interestingness confirmation (point 2) already replayed up to N, then the frontend final replay (point 6) replays up to N again on the same low-p blob.
refs: src/run_lifecycle.rs:599-644, hegel-c/src/native/test_runner.rs:533-545

## [HIGH] 'Cases no longer need stamping before start' contradicts what the fallback report requires
All capture decisions are made before the body runs: run_test_case computes capture_at_discovery = !is_final && c_tc.is_nondeterministic() and should_emit at case start (run_lifecycle.rs:286-302); should_emit gates TestCase emit — with emit off, draws/notes are never recorded into the document (test_case.rs:633,907-908,932), so drawn values cannot be rendered retroactively — gates CAPTURE_BACKTRACE (whose doc says paying it for every discarded shrink probe 'is the dominant cost of failing-heavy property runs, and is far worse on Windows', run_lifecycle.rs:39-46), and gates diagnostic rendering (line 326). So when nothing reproduces, a failure discovered before the flip (or on the un-stamped first case if the sacrifice is removed) yields only the panic payload string and origin — no values, no notes, no backtrace, no thread info. The alternatives each break something: always-capture pays the documented dominant cost on every case; and once ND runs shrink (unlike today, where ND stops at the first bug and skips shrinking entirely, test_runner.rs:473), stamping every case ND makes every failing shrink probe pay render+backtrace+line-buffering — thousands of probes. The design must pick a capture policy; 'unify reporting and drop the stamp' is not free.
refs: src/run_lifecycle.rs:286-302, src/run_lifecycle.rs:39-46, src/test_case.rs:633, src/test_case.rs:907-908, hegel-c/src/native/test_runner.rs:473

## [HIGH] 'DB reuse divergence' as an ND flip/persist site misclassifies ordinary code changes as nondeterminism
Cross-run divergence (a stored entry no longer replays Interesting) is today silent deletion by design (test_runner.rs:267-272; changelog: stale DB entries discard silently, only blobs fail loudly) because it overwhelmingly means the user edited the test/generators or fixed the bug — and the within-run mismatch check cannot fire on the first replay of a stored entry (the per-run tree is empty; a stored value that no longer fits a draw is punned by resolve_choice, state.rs:2442-2492, never errored). If reuse divergence sets and persists the ND flag, every generator tweak and every bug fix stamps a deterministic test ND, degrading its subsequent runs (no novel-prefix tree, N-fold reuse retries, ND shrink machinery) until the clearing heuristic happens to fire. Detection must count only within-run evidence: same run, same prefix, different structure/verdict.
refs: hegel-c/src/native/test_runner.rs:267-272, hegel-c/src/native/core/state.rs:2442-2492

## [MEDIUM] ND persistence is inert in CI, where flaky tests actually matter
Settings::for_ci sets Database::Disabled in CI by default (runner.rs:161-166), and HEGEL_DATABASE=disabled is the env override. So 'persist per-test ND status so later runs start in ND mode' never happens in the default CI configuration: every CI run re-detects ND mid-run, making the first-detection degraded-report path (unstamped pre-flip cases, no capture) the steady state exactly where nondeterministic failures bite. Needs a decision: an ND-status store not gated on the corpus database, an env-var override, or explicit acceptance that CI always runs the detect-and-degrade path.
refs: src/runner.rs:154-180

## [MEDIUM] Flag clearing on 'zero divergence observed' flaps for passing-but-still-ND tests
An ND-mode run only observes divergence via re-executions of the same prefix (confirmation replays, reuse retries, shrink passes). A test that is still nondeterministic in generation but currently PASSES has no failures, hence no confirmations and no shrink — and with the data tree disabled in ND mode (the sketch's acceptable fallback) generation-phase divergence is invisible too. Zero divergence is then observed vacuously, the flag clears, the next run starts deterministic, hits the tree mismatch, and flips again: alternate-run flapping (Warn: warning spam every other run; Error: whether the run aborts depends on which phase of the flap it starts in). Clearing needs positive evidence — deliberate re-execution probes in the ND run — not absence of evidence.
refs: hegel-c/src/native/test_runner.rs:1084-1096, hegel-c/src/native/data_tree.rs:261-292

## [MEDIUM] The frontend-detected flip site (final blob replay flake) cannot participate in the mechanism
The FLAKY_DIAGNOSTIC panic fires after the engine future has completed (run_lifecycle.rs:620-624). At that point: (a) shrinking cannot be re-entered, and the counterexample was shrunk under deterministic assumptions with no probability ratchet, so its failure rate may already be arbitrarily low; (b) no discovery capture exists — the entire run had emit off because it was deterministic-mode throughout; (c) the frontend has no way to write the persisted ND flag: the C ABI exposes no database operations (only hegel_settings_set_database), the DB is engine-owned. Under Quiet the best available is retry-N then a payload-only report, and the ND status is lost for the next run. The design must either move the final replay engine-side or add a post-run ABI call to record ND status, and explicitly accept the degraded report at this site.
refs: src/run_lifecycle.rs:599-644, hegel-c/src/lib.rs:1061

## [MEDIUM] Strictness ownership is split across the ABI and the FAILED_NONDETERMINISTIC contract change is a coordinated binding break
Flip sites are four engine-side plus one frontend-side, so nondeterminism_strictness must live in frontend Settings, be forwarded via a new hegel_settings_set_* in SettingsHandle::build, and be honored independently by both sides — RunError variants are already indistinguishable over the ABI (all collapse to one string via hegel_run_result_error, hegel-c/src/lib.rs:1300-1323), which is tolerable only because Error mode keeps aborting. Separately, hegel.h documents FAILED_NONDETERMINISTIC as 'failures carry no reproduce blob... the engine stamps every case of such a run nondeterministic up front... precisely so the caller captures each case's output' (hegel.h:207-218) — the unified design changes both halves of that contract for every language binding, and c_abi_inprocess.rs:1236-1242 pins the stamping (asserts is_nondeterministic == cases > 1). An old binding against a new engine gets un-stamped failable cases and blob-carrying ND failures it will ignore. This is a breaking ABI-semantics change needing coordinated rollout, not an additive setting.
refs: hegel-c/src/lib.rs:1300-1323, hegel-c/include/hegel.h:196-218, hegel-c/tests/c_abi_inprocess.rs:1236-1242, src/ffi.rs:123-220

## [MEDIUM] Confirmation/boost replays corrupt run accounting and the just-shipped event statistics
record_run counts every execution: a passing confirmation replay increments valid_test_cases — eating the settings.test_cases budget that gates the generation loop (test_runner.rs:321) — plus calls and total_test_time (TooSlow input). During generation, collect_statistics is true (set at 293, cleared at 471) and every Valid/Interesting execution feeds RunStatistics as a separate case (test_runner.rs:1106-1108, events.rs:29-43): N-replay confirmations inflate the denominator and failure-correlated event fractions, and a boost phase repeatedly re-running a failing candidate to estimate its failure rate feeds the same events dozens of times. The 0.36.1 changelog promise ('fraction of generation-phase test cases each event occurred in') silently changes. test_function needs a replay/measurement bit that excludes an execution from counters, budgets, and statistics — no such bit exists today.
refs: hegel-c/src/native/test_runner.rs:293, hegel-c/src/native/test_runner.rs:471, hegel-c/src/native/test_runner.rs:1097-1108, hegel-c/src/native/events.rs:9-43

## [MEDIUM] Multi-run confirmation routed through the existing replay chokepoint would be served from the tree cache, observing zero fresh randomness
cached_test_function serves any fully-recorded path from the tree via simulate_full WITHOUT executing the body, for any status including Interesting (test_runner.rs:1196-1224); all shrink probes go through it (EngineShrinkProbe, 1232-1263). With the data tree restored for ND runs (design point 4), an N-replay confirmation or a repeated shrink-pass predicate using this chokepoint returns the same cached verdict N times — instant, spurious confirmation, and the loop-until-K-dry fixpoint spins on stale conclusions. Only the pre-shrink verify bypasses the cache today (test_function directly, 536-537). The design must state that ND-mode confirmations and probes bypass simulate_full, or define how conclusions-as-distributions are sampled on a cache hit; otherwise the 'single-run predicate' is not a sample at all.
refs: hegel-c/src/native/test_runner.rs:1196-1224, hegel-c/src/native/test_runner.rs:1232-1263, hegel-c/src/native/test_runner.rs:536-545

## [MEDIUM] #[reproduce_failure] and blob-handle replay are unspecified under the new blob format
data_source_for_blob builds NativeTestCase::for_choices(choices, None, None) — no RNG and no continuation budget (embed.rs:87-103) — so an ND blob that reaches an ND node whose recorded branches no longer fit cannot generate fresh values (the draw surfaces as StopTest/overrun), and there is no stated entropy source for ND blob replay. drive_blob_replay executes the blob exactly once and panics 'the supplied failure blob no longer reproduces a failure' on a pass (run_lifecycle.rs:721-736) — for a p=0.1 bug that message fires 90% of the time. The frontend never decodes blobs, so it cannot know a blob needs ND retry semantics without a new ABI surface (an out-param on hegel_test_case_from_blob or a blob-query function). The same applies to the FAILED-path final replay handles the frontend builds from ND blobs.
refs: hegel-c/src/embed.rs:87-103, src/run_lifecycle.rs:691-737

## [MEDIUM] Caveated report incoherence: the per-origin capture is not the execution the blob encodes
If the per-origin capture is taken at first discovery, it holds the unshrunk case — often huge — while the printed blob encodes the shrunk sequence; when no replay reproduces, the report shows values from an execution unrelated to the blob the user is told to replay. Refreshing the capture on every interesting execution reintroduces the capture-cost problem on every failing shrink probe (see the stamping finding); refreshing only at checkpoint-validation k-samples is a plausible middle but unstated. Also: per-origin captures can be stale for origins the engine drops (report_multiple_failures=false keeps only the smallest sort-key origin, test_runner.rs:621-626) and missing for origins whose only frontend-Interesting observations predated the flip — the current hard asserts (stash.expect at run_lifecycle.rs:590; failure-has-no-blob internal error at :615) become reachable states and must turn into graceful degradations.
refs: src/run_lifecycle.rs:589-598, src/run_lifecycle.rs:612-615, hegel-c/src/native/test_runner.rs:617-626

## [LOW] Reuse-phase N-retry cost has no budget and the gating choice reintroduces today's corpus-loss hazard
Reuse replays up to desired_size = max(2, ceil(test_cases*0.1)) entries (~10 by default, with secondary top-up, test_runner.rs:207-230) before generation, and no health check covers the reuse phase (TooSlow only accumulates during generation while valid<10). N-retrying each stale entry after a bug fix multiplies startup latency by N for slow tests with zero budget protection. If retries are gated on the persisted ND flag to avoid that, then an ND test whose flag was cleared (or whose DB is disabled) is back to today's hazard: one lucky passing replay silently deletes the counterexample from both corpora (267-272).
refs: hegel-c/src/native/test_runner.rs:207-230, hegel-c/src/native/test_runner.rs:267-272

## [LOW] replay_aligned never holds under ND, so a persisted ND failure re-shrinks with the expensive machinery every local run
The skip-shrink optimization requires a primary entry to replay Interesting with node-for-node identical values (test_runner.rs:249-263); ND nodes and fresh-generation continuations make exact alignment essentially impossible, so every `cargo test` on a machine with the failure in its DB re-runs the multi-run ND shrink (K-dry fixpoint, checkpoint samples, boost phase) from scratch until the bug is fixed. Consider ND-aware alignment (aligned modulo ND-branch selection) or persisting an already-shrunk marker beside the ND flag.
refs: hegel-c/src/native/test_runner.rs:249-263, hegel-c/src/native/test_runner.rs:473

## [LOW] Default Quiet silently repurposes three pinned user-error signals
tests/test_flaky_replay.rs and tests/test_flaky_global_state.rs pin the FLAKY_DIAGNOSTIC and 'Your data generation is non-deterministic' abort messages that Quiet suppresses; users who rely on those as accidental-nondeterminism lint lose the signal with no notice (the owner's constraint, but it means Warn is the only mode where the lint survives, and the docs/changelog surfaces that promise flaky-detection — hegel-c/CHANGELOG.md:288, rustdoc determinism sections — all need renegotiating). Both crates need RELEASE.md entries; zerover classes the ABI-semantics changes as minor.
refs: tests/test_flaky_replay.rs:1-39, tests/test_flaky_global_state.rs:9-14, src/run_lifecycle.rs:479-487

# IMPROVEMENTS
## Restrict ND detection to within-run evidence and keep cross-run divergence outcome-neutral
Only flip/persist on: same-run tree kind mismatch, same-run verify/confirmation verdict flips, and the frontend final-replay flake (once it has a channel). Treat DB-entry non-reproduction as what it is today — probable staleness — with N-retry-before-delete as a reliability improvement that never writes the ND flag by itself; optionally count it as weak evidence only when the entry's choices replay structurally identically but the verdict differs within the same run's retries.

## Make capture policy explicit: capture at confirmation, not at discovery or on every probe
Since confirming a failure already replays it up to N times engine-side, mark exactly those confirmation executions as capture-enabled (a per-case 'capture' stamp over the existing is_nondeterministic ABI slot, set by the engine when offering a confirmation replay). The frontend then renders document+diagnostic+backtrace only for executions that are candidates for the report, keeping shrink probes cheap, giving the caveated fallback a capture that corresponds to the current (shrunk) incumbent, and removing the need to stamp every case — this also cleanly replaces the sacrificed-case trick, because the first failing case gets confirmed (and captured) immediately after discovery.

## Add a replay/measurement flag to test_function
One boolean threaded into record_run that skips: valid/invalid counters and budgets, statistics.record_case, targeting records, first/last-bug markers, and Persister.record — used by confirmation replays, boost-phase measurements, and checkpoint validations. Without it every quantitative behavior of the runner (budgets, health checks, the new statistics feature) silently changes meaning.

## Version the new blob format and expose blob kind over the ABI
The blob prefix byte is already the natural version gate (unknown prefix = undecodable, loud). Add prefix 2/3 for ND blobs and either an out-parameter on hegel_test_case_from_blob or a hegel_blob_info query so drive_blob_replay and the FAILED-path final replay can select N-retry semantics and an ND-aware 'did not reproduce this time (expected for a nondeterministic failure)' message. Give ND blob replay an explicit entropy source (settings seed or OS entropy) plus a continuation budget in data_source_for_blob.

## Persist ND status independently of the corpus database decision, or say CI is detect-only
If the flag stays in the corpus DB, state explicitly in docs and the design that CI (Database::Disabled default) always runs detect-and-degrade, and make sure the degraded path is good enough to stand alone — because it will be the primary experience of this feature for most users.

## Clear the ND flag with positive evidence
An ND-mode run should re-execute a small sample of its own realized cases (or its reuse entries) k times and clear only when all re-executions are structurally and verdict-identical — turning 'zero divergence observed' from vacuous absence into an actual test, and preventing the passing-but-still-ND flap.
