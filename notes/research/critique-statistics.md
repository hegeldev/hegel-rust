# Adversarial review of design sketch v0: statistics

> Compiled 2026-09-02 against commit a0185a65. The sketch under review is `sketch-v0.md`.
> These findings drove the v0 -> v1 changes recorded in `../design.md` and `../decisions.md`;
> unresolved ones appear there under "Known risks" and "Deferred decisions".

VERDICT: The ratchet/boost/checkpoint architecture is directionally workable, but as sketched its statistical calibration contradicts its own 10% target at three independent points (N=10 confirmation misses 35% of p=0.1 bugs; small-N DB replay deletes genuine entries with ~73% probability per run; origin-splitting pushes per-origin p below the target the arithmetic assumes), and the ratchet's "deterministic" class is assigned from samples that stop-at-first-failure confirmation truncates to near-zero power, producing misclassification that paralyzes shrinking. Separately, two acceptance paths in the existing code (Persister::record and update_interesting) accept any shortlex-smaller interesting run with no probability gate, so the "must not lower failure probability" mandate is violated by persistence/reporting even with a perfect shrinker ratchet, and the boost phase cannot "reuse the Optimiser" as claimed — its budget gate exits when a failure exists, failure rate is not an observable it can score, and its climber cannot step Clone nodes, which hold the structure of the declared top workload.

## [HIGH] Ratchet class 'deterministic = never seen passing' is assigned from a truncated, near-zero-power sample
Confirmation (area 2) stops at the first failure, so a bug entering shrinking has observed history of at most (t-1) passes + 1 failure with t<=10 — and with probability p the very first replay fails (t=1), giving ZERO observed passes. A p=0.7 bug enters shrinking classified 'never seen passing' 70% of the time on t=1, or 34% even after 3 independent runs (0.7^3). Once misclassified deterministic, the sequential test demands m consecutive failures from every candidate: at true p=0.7, P(accept)=0.7^m (2.8% at m=10), so essentially all true reductions are rejected, the 300s deadline burns proposing doomed candidates, and the run reports a barely-shrunk case. This also defeats the mandate 'if shrinking reaches a deterministically-failing region, stay there' — the shrinker can never move to reach it. Conversely, for the class to actually certify p>=0.9 at 90% confidence requires n>=22 consecutive failures (0.9^22=0.098): either the class is expensive to assign honestly or it is noise. Demotion semantics are unspecified: if a 'deterministic' incumbent passes once during checkpoint validation and demotes, the ratchet is not a ratchet; if it never demotes, misclassification is permanent. Cheapest fix: classes are confidence lower bounds on p (Jeffreys/Clopper-Pearson LCB) computed from untruncated samples gathered AFTER the confirming failure (or from boost-phase holdout runs), with explicit demote-with-hysteresis rules; acceptance gauntlets become SPRTs against the incumbent's LCB with stated alpha/beta rather than 'm consecutive failures' (which is an SPRT whose alternative is p=1 and is maximally fragile).
refs: hegel-c/src/native/shrinker/mod.rs:312-348, hegel-c/src/native/test_runner.rs:521-569, hegel-c/src/native/core/mod.rs:77-84

## [HIGH] Persister::record and update_interesting accept on raw shortlex+interesting, bypassing the ratchet entirely
record_run runs for EVERY execution (shrink probes included) and, on Status::Interesting, both persists any shortlex-smaller sequence to the primary DB key immediately (Persister::record, test_runner.rs:913-936, keyed only on sort_key(nodes) < sort_key(last_saved)) and replaces the in-memory per-origin best (update_interesting, test_runner.rs:864-879). Neither path knows about the ratchet or checkpoint validation. Concrete failure: during an ND shrink, a candidate with true p=0.02 fails once by luck; the ratchet's sequential test correctly rejects it, but the single interesting run has already displaced the good primary DB entry (moved to secondary) and saved the p=0.02 sequence as primary. The next CI run's reuse phase replays that entry up to 'small N', it almost surely doesn't reproduce (0.98^N), and it is deleted — so the design's per-run drift protection is defeated at the persistence layer no matter how good the shrinker statistics are. Checkpoint rollback as sketched restores current_nodes but says nothing about un-persisting; the Ctrl-C-safety rationale for incremental persistence makes 'persist only at the end' unattractive, so the fix must be: gate both paths on ratchet-accepted improvements (persist at acceptance, re-persist at rollback), and treat raw interesting probe hits as evidence only.
refs: hegel-c/src/native/test_runner.rs:913-936, hegel-c/src/native/test_runner.rs:864-879, hegel-c/src/native/test_runner.rs:1113-1124, hegel-c/src/native/test_runner.rs:881-889

## [HIGH] Checkpoint rollback against the LAST checkpoint lets p decay geometrically; single-run acceptance supplies the drift
Drift supply: a single-run predicate accepts a candidate with true p' with probability p', so a pass proposing m=20 low-p (p'=0.05) reductions adopts one with probability 1-0.95^20=0.64 — and aggressive-first proposal order (coarse deletion, delete_chunks try big cuts first) is plausibly anti-correlated with p for concurrent workloads (smaller sequences = fewer racing operations). Drift detection: a k=10 checkpoint with rollback threshold at half the baseline misses a genuine halving of p (0.9->0.45) with probability P(Bin(10,0.45)>=4) ~= 0.73; and because each passed checkpoint RE-BASELINES at the collapsed rate, halvings compound across ~33 pass boundaries x several fixpoint iterations — p can fall 0.9->0.1 within a few passes with substantial probability while every individual checkpoint reads OK. Meanwhile a tight threshold thrashes: alpha=5% per checkpoint x ~150+ checkpoints = ~8 spurious rollbacks per shrink, each discarding a full pass of real progress, and after rollback the same pass re-runs and re-accepts the same drifting candidate with the same probability (no memory) — oscillation until the 300s deadline. Fix: anchor the rollback floor at a monotone value (boost-phase holdout p-hat LCB, or the class floor), never the previous checkpoint; poison rolled-back candidates (negative ledger) so they cannot be re-accepted; state the allowed total drift as a design number.
refs: hegel-c/src/native/shrinker/mod.rs:312-348, hegel-c/src/native/shrinker/scheduling.rs:112-189, hegel-c/src/native/shrinker/coarse.rs:21-71, hegel-c/src/native/core/mod.rs:84

## [HIGH] N=10 confirmation and 'small N' DB reuse arithmetic contradict the stated 10% target
At the design's own floor p=0.1: confirmation miss = 0.9^10 = 0.349, so ~35% of runs on a genuine near-threshold bug degrade to the caveated discovery-capture report; N=10 reliably (95%) confirms only p >= 1-0.05^(1/10) = 0.26, i.e. the de facto confirmation threshold is 26%, not 10% (need N=29 for 95% at p=0.1, N=22 for 90%). DB reuse 'replays each stored entry up to a small N before deleting': per-run retention is 1-(1-p)^N — at p=0.1, N=3 gives 27% retention (73% chance the counterexample is deleted on the very next run; survival across 3 runs = 2%), so persistence of ND failures is cosmetic unless N>=22 or deletion is replaced by demotion. Also unspecified: whether the pre-shrink verify uses the same N-run confirm; if a failed confirm skips or weakens shrinking, 35% of near-threshold runs additionally report unshrunk, making shrink quality a coin flip run-to-run. Fixes: persist p-hat (and sample size) alongside the blob and derive each replay budget as N = ceil(ln(delta)/ln(1-p_LCB)); never hard-delete ND-flagged entries on non-reproduction (demote to secondary / age out by consecutive-miss count); note stop-at-first-failure keeps expected cost at min(1/p, N) ~ 6.5-10 runs for genuine bugs so large N is affordable exactly when it matters.
refs: hegel-c/src/native/test_runner.rs:198-283, src/run_lifecycle.rs:599-644, hegel-c/src/native/test_runner.rs:484-515

## [HIGH] Every p-statistic's population is undefined: per-origin vs per-test, and pooled-candidate vs realized-timeline
(a) Origin split: the shrink predicate matches status==Interesting AND origin==target_origin (EngineShrinkProbe, test_runner.rs:1258-1260), and ND workloads split failures across panic sites run-to-run — plus unjoined-thread panics all collapse to 'Panic at <unknown>' (run_lifecycle.rs:200-217). A test failing 10% of the time across two origins has per-origin p ~ 0.05, below every arithmetic in the design; all miss rates computed at p=0.1 roughly double in exponent. Confirmation semantics (accept any-origin failure, or only the reported origin?) is unspecified and changes both the miss rate and what the 'first failing execution rendered fresh' shows — it can render a different bug than was shrunk. (b) Timeline pooling: with ND nodes, a proposed candidate realizes different timelines across runs, so its pooled p-hat = sum over timelines of P(realize)·p(fail|timeline); but consider() adopts the ACTUAL realized nodes of the one failing run (mod.rs:340-346), and replay of the incumbent pins the failing branch (failing-timeline-first ordering) — so acceptance is decided on the pooled population while incumbent validation measures p(fail|pinned), generally higher. The ratchet then compares incompatible quantities with a systematic anti-shrink bias (candidates measured pooled vs incumbent measured pinned), and if the branch cap evicts the failing branch, replay silently reverts to fresh generation and the incumbent's measured p collapses for reasons unrelated to the last pass — phantom rollbacks. Fix: define every statistic per (origin, realized-timeline); key the evidence ledger by realized nodes, use candidate-level stats only for routing; restate the 10% target per-origin or merge origins for ND runs.
refs: hegel-c/src/native/test_runner.rs:1232-1263, src/run_lifecycle.rs:200-217, hegel-c/src/native/shrinker/mod.rs:340-346

## [MEDIUM] Boost phase cannot 'reuse the Optimiser': its budget gate, score plumbing, and climbable-node set all contradict the plan
Three verified contradictions with targeting.rs: (1) Optimiser::budget_exhausted's first clause is !self.engine.interesting.is_empty() (targeting.rs:113-117) — the optimiser refuses to run once any failure exists, which in a boost phase is always; (2) scores flow through run.target_observations, recorded only for status >= Valid runs that called hegel_target (test_runner.rs:1102-1104), and run_trial is a single execution (targeting.rs:128-135) — 'observed failure rate' is not an observable a single trial produces, so hill_climb/try_replace need k-run wrappers and a synthetic score channel throughout, i.e. a rewrite, not reuse; (3) is_climbable admits only Integer/Float/Boolean/Bytes (targeting.rs:301-309) and hill_climb walks top-level current_nodes — Clone nodes (where concurrent-stateful structure lives) and Strings are unsteppable, so for the declared #1 workload the climber has no lever on the interleaving/step structure that actually controls failure probability; it can only twiddle scalars outside the clone streams. Also FindInteger drives the climb and converges deterministically on recorded verdicts (search.rs:95-123): one noisy k-run verdict in the Grow phase truncates the search, and in Narrow it corrupts the lo-holds/hi-fails invariant, silently converging to a wrong step size. The Optimiser also has no wall-clock deadline at all (budget is valid-cases/calls only) — unbounded boost time on slow concurrent bodies unless one is added.
refs: hegel-c/src/native/targeting.rs:113-135, hegel-c/src/native/targeting.rs:162-242, hegel-c/src/native/targeting.rs:301-309, hegel-c/src/native/test_runner.rs:1102-1104, hegel-c/src/native/shrinker/search.rs:95-123

## [MEDIUM] Winner's curse: max-recording of noisy k-run failure-rate estimates inflates the boost result and poisons the ratchet class
TargetingState::record keeps the max-ever score with its choices (targeting.rs:36-52), and try_replace commits ties and strict improvements (targeting.rs:281-295). With k=10-run failure-rate estimates, two candidates of equal true p produce a 'strict improvement' ~40% of steps and a committed tie besides, so the climb performs a lateral random walk while current_score ratchets up as the max of binomial draws: at true p=0.5, k=10, after ~50 trials E[max p-hat] ~ 0.9. Consequences: (a) the climb freezes — real improvements must beat the inflated bar (P(Bin(10,0.5)>=9)~1%), so the boost phase reports 'no further improvement' while having found nothing; (b) the inflated p-hat, if used to seed the ratchet class or checkpoint baseline, classifies a p~0.5 incumbent as high-p/deterministic, and every subsequent shrink candidate faces a sequential test calibrated to a probability the true process cannot deliver — shrink paralysis identical to the misclassification hole but caused upstream. The alternative score '-attempts-to-first-failure' is a heavy-tailed geometric and is strictly worse under max-recording (one lucky first-try failure of a p=0.05 candidate scores like determinism). Fixes: score by a lower confidence bound (Jeffreys LCB), which is winner's-curse-resistant to maximize; re-estimate the final winner on a FRESH holdout sample before it seeds any class/baseline; prefer a bandit allocation (successive halving over candidate perturbations) to hill-climbing point estimates.
refs: hegel-c/src/native/targeting.rs:36-52, hegel-c/src/native/targeting.rs:281-295

## [MEDIUM] Sequential-test and re-proposal costs: ND mode removes the data-tree dedup that made repeated proposals free
In today's engine, repeated candidates cost nothing: cached_test_function serves any recorded path from the lossless tree without executing (test_runner.rs:1196-1224), and the shrinker deliberately has no other cache. Every retry scheme in the design (loop-until-K-dry re-stepping all ~33 passes; sequential gauntlets; k-run checkpoints) re-proposes previously-judged candidates — and in ND mode the tree cannot serve verdicts (serving a cached outcome/distribution would freeze results exactly like today's simulate_full), so every re-proposal is a fresh execution. Costs: certifying 'candidate is deterministic' vs a deterministic incumbent at 95% needs m=29 consecutive failures; each REJECTED near-miss candidate (p=0.9) costs E[min(Geom(0.1), 29)] ~ 9.5 runs and, with no memory, is re-adjudicated from scratch every K-dry iteration. K-dry itself: P(a remaining p=0.1 reduction survives K dry iterations) = 0.9^K, so K~22 for 90% power, and each iteration re-executes the full proposal set — at equal statistical power loop-until-K-dry costs ~22x the suite versus ~10x for the 'rejected' per-candidate-N-with-early-exit design, so the stated preference is plausibly backwards on cost; only an experiment settles it. Cheapest fix: an evidence ledger keyed by realized candidate (runs, failures — a posterior carried across proposals, passes, and iterations) replacing the tree's dedup role, so re-proposals resume accumulated evidence instead of restarting; make K and per-pass retry budgets functions of the incumbent's p-hat LCB rather than constants.
refs: hegel-c/src/native/test_runner.rs:1196-1224, hegel-c/src/native/shrinker/scheduling.rs:112-189, hegel-c/tests/embedded/native/shrinker_cache_tests.rs:1-8

## [MEDIUM] Existing budget constants all count physical executions and will misfire under multi-run predicates
(1) Stall guard: after the first improvement, consider/probe silently drop every candidate once calls - calls_at_last_shrink >= max_stall (init 500, mod.rs:334-338); with k-run validations and sequential gauntlets inflating physical calls 10-30x per logical candidate, the guard latches after ~15-50 logical candidates, and the outer K-dry iterations then 'measure' a latched guard — an all-quiet iteration reads as a fixed point when candidates were never run (fixate resets the window per iteration at scheduling.rs:120, but 500 calls/iteration across 33 passes is ~1-2 candidates per pass at k=10). (2) MAX_SHRINKS=500 improvement cap (mod.rs:331-333): noise-accepts that later roll back still consumed improvements unless rollback decrements — Stop can fire on a barely-shrunk target. (3) MAX_SHRINKING_SECONDS=300 becomes the binding constraint for the top workload (slow concurrent bodies x ~10x call multiplier); absorb_stop silently keeps a near-unshrunk example and prints slow_shrink_warning every run — expect systematically worse ND shrink quality with no signal other than the warning. Boost-phase time is additionally unbudgeted (see Optimiser hole). (4) Confirmation replays flow through record_run: a passing replay increments valid_test_cases (test_runner.rs:1109-1111), eating the default 100-case budget (one 10-replay false alarm = 10% of the run) and inflating the denominators of FilterTooMuch/TooSlow health checks; replays must be excluded from budget/health counters. (5) STOCHASTIC_MAX_FAILURES=6 (scheduling.rs:116): if all passes become effectively stochastic under a noisy predicate, 6 retries detect a single p=0.1 reduction with probability 1-0.9^6=0.47 per pass visit — pass-level fixation remains the dominant miss source regardless of the outer loop. All of these need logical-candidate counting or 1/p-hat scaling.
refs: hegel-c/src/native/shrinker/mod.rs:181-209, hegel-c/src/native/shrinker/mod.rs:331-338, hegel-c/src/native/shrinker/scheduling.rs:112-189, hegel-c/src/native/core/mod.rs:72-84, hegel-c/src/native/test_runner.rs:1097-1125, hegel-c/src/native/test_runner.rs:834-859

## [LOW] Checkpoint validation sample is biased and multiplicity-uncorrected
A checkpoint taken right after an acceptance conditions on the accepting failure: single-run acceptance means the incumbent was adopted BECAUSE it just failed, so including that run (or sampling immediately in the same environment epoch) biases p-hat up by ~1/k and understates drift. With ~33 passes x several iterations, 150+ checkpoints at per-test alpha=5% expect ~8 spurious rollbacks per shrink. Fixes: exclude the accepting run from all estimates; checkpoint every few passes rather than every pass, or apply an alpha-spending schedule; log rollback counts so thrash is observable.
refs: hegel-c/src/native/shrinker/mod.rs:398-415, hegel-c/src/native/shrinker/scheduling.rs:112-189

## [LOW] last_checkpoint_nodes is cited as rollback precedent but is only a diff baseline
last_checkpoint_nodes/all_changed_nodes (mod.rs:210-218, clear_change_tracking at 450-454) exist to feed lower_common_node_offset with changed-index sets; nothing restores current_nodes/current_spans/improvements/downgraded from them, and downgraded (the displaced-sequence list consumed for DB secondary-key demotion) has no un-push. Real rollback needs a new snapshot type covering nodes, spans, improvement count, the downgraded list watermark, and the Persister's last_saved map — plus the poison set for rolled-back acceptances. Small but easy to underestimate.
refs: hegel-c/src/native/shrinker/mod.rs:210-218, hegel-c/src/native/shrinker/mod.rs:450-454, hegel-c/src/native/shrinker/mod.rs:177-180

## [LOW] Caveat fatigue: at the target probability the 'environment modification' hypothesis is almost always wrong
With N=10 confirmation, a genuine p=0.1 bug produces the caveated both-hypotheses report on ~35% of runs; across a suite of ND tests users will see the caveat constantly for real bugs, learn to ignore it, and lose the one case where it matters (a truly vanished failure). Weight the wording by evidence: report the measured discovery-phase rate and the replay tally ('failed 3 of 10 replays; observed failure rate during the run: 12%') and reserve the environment-modification hypothesis for entries whose persisted p-hat made non-reproduction genuinely surprising (e.g. p-hat LCB > 0.5 yet 0/N replays).
refs: src/run_lifecycle.rs:599-644, src/run_lifecycle.rs:451-477

# IMPROVEMENTS
## Build a pure-simulation calibration harness before touching the engine
All open constants (confirmation N, checkpoint k, gauntlet m, K-dry, stall scaling) are properties of the scheduler logic, not the engine. Implement the ratchet/checkpoint/K-dry state machine against synthetic landscapes — candidate -> true p as (a) smooth p(sequence size), (b) cliff-edge, (c) timeline mixtures with branch-cap eviction — driving it with Bernoulli draws, and measure final size, final true p, and execution count. A few hundred lines settles the loop-until-K-dry vs per-candidate-N cost question, the drift-per-pass and rollback-thrash rates, and gives defensible defaults; it also becomes a regression test for the eventual implementation.

## Replace ad-hoc rules with confidence bounds and one evidence ledger
Unify every decision on a per-(origin, realized-timeline) evidence ledger of (runs, failures) that persists across proposals, passes, iterations, and — via the DB — runs. Class = Jeffreys LCB on p from that ledger (never 'never seen passing'); acceptance = SPRT against the incumbent's LCB with stated alpha/beta; rollback floor = monotone anchored value (boost holdout LCB), not the last checkpoint; confirmation and DB-reuse replay budgets = ceil(ln(delta)/ln(1 - p_LCB)) from the persisted estimate. This one structure fixes the truncated-sample class, the compounding drift baseline, the re-proposal cost blowup, and the N-vs-10% contradictions simultaneously.

## Gate all three acceptance paths on the same predicate
The shrinker's consider(), update_interesting, and Persister::record must accept on the same ratchet event or the weakest path defines the system's real behavior. Cheapest shape: record_run in ND mode treats interesting probe results as ledger evidence only; persistence and the interesting map update fire from an explicit 'accepted' callback out of the shrinker (and rollback re-persists the checkpoint incumbent). Keep incremental persistence for Ctrl-C safety by persisting the current validated incumbent, not the latest lucky failure.

## Boost via bandit allocation over mutations, not Optimiser hill-climbing
Given is_climbable excludes Clone/String nodes, hill-climbing scalars cannot boost the top workload. A better fit for 'raise p before shrinking': generate candidate variants with the existing mutation machinery (span duplication in try_span_mutation, donor splices), then run successive halving over them with the failure-rate ledger — allocation by LCB avoids the winner's curse, spends runs only on promising variants, and needs no per-kind step logic. Re-estimate the winner on a holdout sample before it seeds the ratchet class, and give the phase its own wall-clock budget separate from MAX_SHRINKING_SECONDS.

## Exclude replays and validations from run-budget and health-check counters
Confirmation replays, checkpoint validations, and gauntlet runs should increment a separate replay counter rather than calls/valid_test_cases, so the default 100-case budget, should_generate_more's post-bug window, within_invalid_budget, and the FilterTooMuch/TooSlow denominators keep their current meanings; the shrinker's calls/max_stall should count logical candidates (first run of a candidate) with physical runs tracked separately for the wall-clock budget.
