# Adversarial review of design sketch v0: shrink-loop

> Compiled 2026-09-02 against commit a0185a65. The sketch under review is `sketch-v0.md`.
> These findings drove the v0 -> v1 changes recorded in `../design.md` and `../decisions.md`;
> unresolved ones appear there under "Known risks" and "Deferred decisions".

VERDICT: Area 5 as sketched is not implementable against the current shrinker without three prior decisions it leaves open: where ND branch structure lives relative to the flat ChoiceNode sequences every pass, sort_key, and consider() operate on; what replaces the choice-tree cache that currently freezes each path at its first outcome (making all proposed re-sampling silently no-op) while also being the only thing that makes fixate_shrink_passes affordable; and how sticky single-run accepts are prevented from burning the monotone budgets (MAX_SHRINKS=500 improvements, stall windows, the Persister's write-only DB ratchet) faster than checkpoint rollback can recover. The pass-repetition/K-dry loop itself is a small change to fixate_shrink_passes, but its cost model inverts once cache dedup is off, and rollback has no precedent in the code — last_checkpoint_nodes is a diff baseline for lower_common_node_offset, not a snapshot mechanism.

## [HIGH] ND-node representation vs flat shrinker state is unresolved and both options break stated mechanisms
Shrinker::current_nodes, sort_key, replace(), span passes (node-index ranges), NodeGone typed reads, and consider()'s adoption of run.nodes all operate on flat Vec<ChoiceNode>; EngineShrinkProbe returns the single run's realized timeline (NativeDataSource::take_nodes), never a branch structure. If ND nodes (branch head + tree-shaped suffixes) are folded into the sequences the shrinker holds, then sort_key, ChoiceValueKey, with_value/replace, mutation's to_index, flattened_values_len/max_size budget arithmetic, and every span splice must be extended — and the sketched sort key (failing branch first, then branch count) makes an incumbent's key GROW whenever a new timeline is folded in as a branch, so learning more about a node blocks acceptance of genuinely smaller candidates. If instead the shrinker stays flat over realized timelines, item 5's cross-timeline grafting has no access to the failing branch's suffix from inside a pass (branch data lives engine/tree-side only), and 'improvements' can be pure schedule variance: replaying the same candidate realizes different actual_nodes per run, so consider(is_interesting && sort_key(actual) < sort_key(current)) accepts lucky-short timelines unrelated to the candidate mutation. The sketch's items 3 and 5 implicitly assume both representations at once.

## [HIGH] Choice-tree cache freezes verdicts, so every re-sampling mechanism in area 5 silently no-ops; bypassing it inverts the cost model that makes the fixpoint loop affordable
Engine::cached_test_function serves any fully-recorded path from data_tree::simulate_full without executing, for any status, and even with extend>0 (only a predicted EarlyStop falls through). record_tree_full unconditionally overwrites leaf.conclusion on an outcome flip. So: the N-replay failure confirm, the k-run checkpoint sample, and 'run each pass N times' all degenerate to 1 real run + cache hits — a deterministic pass re-stepped on an unchanged target re-proposes the exact same candidates, which are exactly the ones the tree dedups. Turning the cache off for ND makes those repeats real executions: ~33 passes propose O(10^3-10^4) candidate evaluations per outer iteration for a ~50-node target (delete_chunks, node_program_1..5, per-node binary searches, mutate_and_shrink's up to 32 divergent probes per candidate value), and loop-until-K-dry multiplies the terminal sweep by K. At concurrent-stateful execution times the MAX_SHRINKING_SECONDS=300 deadline (run_test_fn short-circuits past it) becomes the binding constraint, so shrink quality is whatever 300s buys. The design needs an explicit cache-epoch/distribution-serving semantics plus a measured cost budget, not 'restore the tree if feasible'.

## [HIGH] Single-run accepts are sticky and burn monotone budgets faster than pass-boundary rollback can recover
consider() accepts on one interesting run; a candidate whose failure probability collapsed to q is accepted with probability q per proposal and there is no un-accept — the sort-key ratchet only descends. With hundreds of candidates per sweep and a 10%-class flaky test, expect tens of spurious accepts per sweep. Each accept: (a) increments improvements toward MAX_SHRINKS=500, after which consider returns Err(ShrinkHalt::Stop) — rollbacks cannot decrement it, so accept/rollback cycles permanently consume the budget; (b) resets calls_at_last_shrink and grows max_stall (accept_improvement), so the stall guard never terminates a noisy shrink; (c) resets failures=0 in fixate_shrink_passes, so even a max_failures=1 deterministic pass loops arbitrarily long. Worst single shape: BinSearchDown/Big probe lo FIRST (state CheckLo), so one lucky failing run at the simplest value teleports the incumbent to a near-zero-probability example in one call. Checkpoint validation at pass boundaries then discards the whole pass's genuine progress along with the drift. The ratchet classes as sketched (deterministic > high-p > low-p) only guard cross-class accepts; within-class drift (0.9 -> 0.15, both 'high-p') is exactly the martingale walk the constraints forbid. The sequential consecutive-failure test must apply to every accept (cheap rejects, m-run accepts), and budget semantics for rollback (improvements, max_stall, failures) must be defined.

## [MEDIUM] ShrinkRun::Full replay is extend=0/deterministic; ND-node 'generate fresh with continuation budget' contradicts it
EngineShrinkProbe::Full routes to cached_test_function(choices, nodes, 0) -> NativeTestCase::for_choices with max_size = flattened candidate length; any extra draw is EarlyStop/Overrun (state.rs pre_choice), i.e. rejected. Item 3's replay rule at an ND node — 'else generates fresh randomly with a capped continuation budget' — means either (a) unmatched-branch candidates overrun and are rejected, so every pass that perturbs an ND region stalls, or (b) all Full replays gain probe semantics (RNG + extension budget), destroying the deterministic-realization invariant that punning, deficit-deletion repair (try_replace_with_deletion computes deficit = expected_len - actual_len), and replay_observing_divergence (whose doc explicitly states 'the realised kind sequence is deterministic') are built on. Branches with different suffix lengths also make every flattened-length budget computation ill-defined: splice_child/NestedCloneProbe (flattened_values_len(&values) + child_extend), coarse's flattened_len + 16, mutation's flattened_len(&snapshot). This needs a decision before any pass logic is touched.

## [MEDIUM] Persister and update_interesting bypass the shrinker's ratchet: spurious minima are written to the primary DB key before any checkpoint validation, and rollback cannot undo them
Every shrinker execution goes through Engine::record_run: any interesting run shortlex-smaller than the last save triggers Persister::record, which writes the new bytes to the PRIMARY key and moves the previously-saved (checkpoint-validated) entry to secondary — immediately, mid-pass, before the design's k-run pass-boundary validation can reject it. update_interesting likewise takes any smaller realization for other origins. A rollback restores Shrinker::current_nodes but not persister.last_saved or the DB, so the primary key systematically ends up holding the most-shrunk, least-reproducible sequence while the validated one sits in secondary; item 6's replay-up-to-N-before-delete on reuse only papers over this inversion. Also note self.downgraded grows on every accept (its doc ties it to secondary-key downgrading) and has no rollback story. Persistence must be gated on the same validation as acceptance, or deferred to checkpoint commits.
refs: hegel-c/src/native/test_runner.rs:1113-1123, hegel-c/src/native/test_runner.rs:913-936, hegel-c/src/native/test_runner.rs:864-879, hegel-c/src/native/shrinker/mod.rs:176-180

## [MEDIUM] 'last_checkpoint_nodes machinery precedent' is false: it is a diff baseline for one pass, not a rollback snapshot
last_checkpoint_nodes/all_changed_nodes exist solely so lower_common_node_offset can find integer nodes that changed together; the baseline is reset only by clear_change_tracking, called at the END of lower_common_node_offset itself (integers.rs:594) — roughly once per outer iteration, nothing like the ~33 pass boundaries the checkpoint scheme needs. Reusing the field for rollback breaks the zig-zag detection (the changed-set would be rebaselined at every pass boundary, before the pass that consumes it runs), and a rollback via plain assignment to current_nodes leaves all_changed_nodes stale (update_change_tracking runs only inside accept_improvement). Rollback needs a new snapshot carrying nodes + spans + a reconciliation policy for improvements/downgraded/persister.last_saved; nothing in the shrinker restores state today.
refs: hegel-c/src/native/shrinker/mod.rs:210-218, hegel-c/src/native/shrinker/mod.rs:423-454, hegel-c/src/native/shrinker/integers.rs:522-596

## [MEDIUM] Mid-shrink ND detection does not exist today, so 'existing abort sites become flip sites' misses the shrink phase entirely
The sketch's item 1 routes flip decisions through 'current abort sites', but during shrinking the choice-tree kind-mismatch diagnostic is silently discarded: cached_test_function does `let (run, _mismatch) = self.test_function(ntc).await?` (test_runner.rs:1222). The only shrink-adjacent abort is the pre-shrink verify replay (test_runner.rs:537-544). A test whose nondeterminism first manifests mid-shrink today just silently overwrites leaf conclusions in the tree; making Quiet-mode flip work there requires new plumbing (propagate mismatch through EngineShrinkProbe/ShrinkHalt, define what happens to the half-finished Shrinker whose current_nodes/tree state were built under deterministic assumptions — restart the origin's shrink in ND mode, or convert in place). ShrinkHalt::Error currently aborts the whole run at `shrinker.shrink().await?` (test_runner.rs:563), so the error channel as-is turns a flip into an abort — exactly what Quiet must not do.
refs: hegel-c/src/native/test_runner.rs:1222, hegel-c/src/native/test_runner.rs:536-544, hegel-c/src/native/test_runner.rs:563, hegel-c/src/native/shrinker/mod.rs:98-118

## [MEDIUM] Nested clone shrinking (the top workload's path) identifies the child by realized position and ratchets on schedule noise; the tree's clone precedent is 'disable on contradiction', not 'branch'
Concurrent stateful failures funnel through shrink_clone_streams: NestedCloneProbe splices a child candidate into the parent template and reads the realized child back from actual.get(i) (clones.rs:65-72), returning (false, empty) when i is no longer a clone node. Under ND the realized stream at i varies per run with the schedule, so the nested Shrinker's consider adopts whatever stream the run happened to realize — its sort-key ratchet then rewards lucky-short interleavings independent of the nested candidate's content, and nested current_nodes stop corresponding to anything replayable. Putting ND branch nodes INSIDE RealizedStream (item 3's 'like Clone's RealizedStream nesting') requires splice_child, CloneRecord::from_values, flattened_values_len, and record_clone_record to understand them; note record_clone_record's existing answer to a contradicting clone stream is to permanently DISABLE the subtree (clone_subtree_disabled, data_tree.rs:338-349) — the codebase precedent for nested nondeterminism is giving up, and item 4's widening has to replace that, not just the top-level kind-mismatch error.
refs: hegel-c/src/native/shrinker/clones.rs:25-127, hegel-c/src/native/data_tree.rs:335-349

## [MEDIUM] Boost phase 'reusing targeting/Optimiser machinery' is mostly new code, not reuse
Optimiser::budget_exhausted returns true the moment engine.interesting is non-empty (targeting.rs), i.e. the optimiser is hard-wired to STOP exactly when the boost phase would start — the gate must invert. Scores flow from in-run target_observations (recorded by TargetingState::record per single run, per label, monotone max, status>=Valid only); 'observed failure rate' or '-attempts-to-first-failure' is a property of repeated executions of the same choices, which nothing in targeting.rs measures — run_trial is one for_probe execution via test_function. hill_climb perturbs only is_climbable integer nodes, adopts realized nodes on any score improvement, and has no origin filter, so boost as-is could migrate the incumbent to a different bug, violating per-origin identity. Also -attempts-to-first-failure is geometric (variance ~1/p^2); hill-climbing on single estimates needs its own sequential-test guard — the same small-sample trap the constraints call out. Reusable: the hill_climb walk skeleton and FindInteger. New: the scoring driver, k-run estimation, origin filtering, gating, and interaction with the tree cache.

## [LOW] Adaptive searches converge on noise with no resume state; pass repetition re-runs whole searches
FindInteger ends its Linear/Grow phase at the first false verdict (P(surviving k doublings) = q^k under per-probe failure prob q), and BinSearchDown/Big converge to arbitrary points under flipped verdicts — safe for correctness (every accept was itself an interesting run) but systematically under-shrinking. The searches are throwaway values with no way to resume from prior bounds, so 'run each pass N times' repeats every search from scratch each step. Note also that a stall-guard-latched consider returns Ok(false) WITHOUT executing (mod.rs:334-337), feeding fabricated 'false' verdicts into searches today — any ND accounting that counts physical runs must keep this silent-false path in view.
refs: hegel-c/src/native/shrinker/search.rs:95-124, hegel-c/src/native/shrinker/search.rs:171-194, hegel-c/src/native/shrinker/mod.rs:331-341

## [LOW] Call accounting already diverges from physical executions; k-run predicates need a defined unit
Shrinker::calls increments once per consider/probe/try_trivial_spans execution, but several observation runs bypass it (coarse.rs reduce_each_alternative's zeroing run at :56, try_replace_with_deletion's observation at deletion.rs:118, minimize_individual_choices' at deletion.rs:193). If ND makes one logical call k physical runs, the stall guard (max_stall, default MAX_SHRINKS=500 against shrinker-local calls) either expires k-fold early (counting physical) or stops bounding wall-clock at all (counting logical). Decide the unit and make the deadline, stall guard, and profiling stats consistent; today they already disagree.
refs: hegel-c/src/native/shrinker/coarse.rs:51-62, hegel-c/src/native/shrinker/deletion.rs:112-121, hegel-c/src/native/shrinker/mod.rs:186-209

## [LOW] consider's equal-sort-key fast path conflates 'is the incumbent' with 'confirmed failing'
consider returns Ok(true) without executing when sort_key(candidate) == sort_key(current) (mod.rs:312-314); passes and adaptive searches read that as predicate-held. Under a distribution-valued predicate this is sound only under an explicit invariant that the incumbent's failing status is maintained externally (the checkpoint validation) — state that invariant, and define sort-key equality for ND-bearing nodes (same failing branch, different suffix trees: equal or not?) before keeping the fast path. The shortlex-worse fast path (mod.rs:316-322) similarly assumes the candidate realizes as proposed, which ND replay weakens further than today's punning does.

# IMPROVEMENTS
## Prototype order
1) Cache/epoch semantics first: add a resampling seam at EngineShrinkProbe/cached_test_function (per-shrink tree epoch or ND-bypass) and measure the cost of one fixate iteration with dedup off on a real ~50-node target — every other mechanism is moot until N replays actually execute N times and the cost is known. 2) Flat-timeline shrink experiment: keep the shrinker flat, add within-class sequential accept (m consecutive failing runs scaled by incumbent class) + pass-boundary checkpoint/rollback with explicit budget rules, on a synthetic non-branching 10%-flaky test; this answers whether ratchets+checkpoints tame drift before any ND-node work exists. 3) ND-node replay semantics in state.rs resolve_choice (branch match vs fresh continuation) and the Full-replay extend question — this decides the representation split and the budget arithmetic. 4) Cross-timeline donor grafting last: the reusable precedents are mutate_and_shrink's replay_observing_divergence + DIVERGENT_RANDOM_ATTEMPTS pattern and try_span_mutation's donor splices (both flat-sequence, random-continuation); genuinely new is branch-addressed suffix storage and constraint-matched forcing at ND nodes.

## Defer persistence to checkpoint commits
Gate Persister::record and update_interesting on shrink-phase validation (e.g. Persister buffers during shrinking and commits at checkpoint acceptance), preserving the Ctrl-C guarantee by committing the last VALIDATED incumbent instead of every raw interesting run. This closes the primary/secondary inversion without touching the DB format.

## Make loop-until-K-dry a stochastic-flag generalization, not a new loop
fixate_shrink_passes already has the exact mechanism: STOCHASTIC_MAX_FAILURES per-pass retry budgets plus the while-any_ran outer loop. Marking passes stochastic under ND (budget scaled by class) reuses the reorder-by-usefulness and stall-window-reset logic unchanged and confines the change to scheduling.rs:131; a separate K-dry outer loop would duplicate progress detection and interact badly with remove_discarded interleaving.

## Charge accepts, not rejects
Keep single-run rejects cheap; make every accept pay the m-consecutive-failure sequential test with m scaled by incumbent class, and exempt validated accepts from the MAX_SHRINKS improvement count (or count checkpoint commits instead of raw accepts). This preserves the constraint's cheap-predicate intent while removing the sticky-accept drift and budget burn in one place (accept_improvement).
