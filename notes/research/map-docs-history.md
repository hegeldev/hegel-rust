## Engine changelog: the concurrent-stateful nondeterminism contract (hegel-c 0.33.0, 2026-08-20)
The authoritative documented contract: creating a state machine with max_concurrency > 1 declares the run nondeterministic; the engine detects it itself ('frontends have nothing to set up front'); 'a nondeterministic run can't be replayed, so discovery is the only chance to capture'; frontends check hegel_test_case_is_nondeterministic at case start and capture the whole trace (only the most recent capture needed, 'because the run will end as soon as a failure is found'); the engine skips 'data-tree recording (and with it novel-prefix generation and the nondeterminism mismatch check), span mutation, the verify and shrink pass (and with it the flakiness check), targeting, and database persistence and reuse'; failing nondeterministic runs report HEGEL_RUN_STATUS_FAILED_NONDETERMINISTIC, frontends skip final replay and print no reproducer; single-test-case runs still report plain FAILED; stateful_step_count now bounds rounds; the choice-sequence shape change invalidated stored DB entries and blobs.

## C header docs: run-flip mechanics and run-status semantics
hegel.h documents hegel_new_state_machine's flip protocol: on a run not already nondeterministic, the FIRST max_concurrency>1 creation is rejected with HEGEL_E_ASSUME (case reported INVALID) and the engine flips the run at that case's end; every LATER case is stamped nondeterministic before it starts so frontends can capture its whole trace including draws made before machine creation; a notice prints once unless quiet; the declared bound counts even if the drawn concurrency is 1; blob replays and single-test-case runs are never rejected. HEGEL_RUN_STATUS_FAILED_NONDETERMINISTIC (value 3) docs say failures carry no reproduce blob, no shrinking, no final replay. hegel_test_case_is_nondeterministic returns whether the case belongs to a run already known nondeterministic. Clone docs: clone shares outcome/budgets but generates from its own choice sequence, 'staying deterministic under replay'; shared collections/pools/state machines from two streams 'makes tests flaky'.

## Frontend capture-at-discovery design (NondetStash)
run_lifecycle.rs documents the frontend half of the contract: capture_at_discovery = !is_final && c_tc.is_nondeterministic() is read once at case start; every interesting case's draw/note lines and panic diagnostic are stashed in NondetStash but READ only when the run verdict comes back FAILED_NONDETERMINISTIC (a frontend-interesting report can lose silently to an engine-side family conclusion, so printing is deferred to the verdict); if the run passes the stash is discarded ('a genuine racy bug resurfaces in a later case'); a deterministic run never reads the stash — its failures replay from reproduce blobs via drive's from_blob path with the client owning final replays.

## Event statistics (PR #431, hegeltest 0.36.1 / hegel-c 0.34.1, 2026-09-02) and nondeterminism exposure
Documented promise: per label, 'the fraction of generation-phase test cases each event occurred in' plus count/min/median/mean/p90/max of numeric observations (Settings::show_statistics / HEGEL_STATISTICS). Implementation: RunStatistics in hegel-c/src/native/events.rs folds one case at a time; module doc says only generation-phase Valid|Interesting cases are recorded because shrink replays 'would re-observe the same shrinking target over and over'. collect_statistics is set to true at generation-phase start (test_runner.rs:293) and false at generation end (test_runner.rs:471); recording happens in record_run gated on collect_statistics && Status::Valid|Interesting (test_runner.rs:1106-1108); rendering at run end when show_statistics (test_runner.rs:628-630). There is NO gating on self.nondeterministic, so nondeterministic (concurrent-stateful) runs still feed statistics; events from concurrent worker clones accumulate into one per-family list whose cross-thread ordering is scheduling-dependent, though bare events are deduplicated per case (order-insensitive) while every event_value observation counts. Separately, concurrent worker output is stamped with wall-clock '[worker N +X.XXXms]' offsets — inherently nondeterministic per-run data shown to users.

RELEVANCE: The documentation layer defines the exact envelope any nondeterminism extension must respect or renegotiate. Today's documented model is binary: a run is either fully deterministic — with strong, repeatedly-promised guarantees (same-seed replay per clone stream, exact blob replay, shrinking to a minimal counterexample, flaky-test detection as a *user error* signal, deterministic report rendering) — or engine-declared nondeterministic (only via max_concurrency > 1 state machines), in which case an enumerated feature set is documented as disabled: data-tree recording, novel-prefix generation, the nondeterminism mismatch check, span mutation, verify+shrink (and the flakiness check), targeting, and database persistence/reuse, with failures reported un-shrunk from the discovering execution and at most one failure per run. Three user-facing messages encode the current assumption that unexpected nondeterminism is a bug in the user's test ('Flaky test detected', 'Your data generation is non-deterministic') rather than something to tolerate — an extension that handles nondeterministic tests would change the meaning of both. The changelogs establish two compatibility surfaces the design must consider: choice-sequence shape (breaks invalidate DB entries quietly and blobs loudly, and are called out per release) and the reproduce-blob/version contract. The unmerged parallel-tests branch adds a third determinism regime (schedule-unreproducible search, deterministic shrink/replay) that a general nondeterminism design should compose with. The just-landed event statistics assume per-case observations during a sequential generation phase and are currently not gated off in nondeterministic runs, so run-level reporting is a surface nondeterminism can scramble (as are the wall-clock worker-offset stamps in concurrent output). Procedurally, any change here needs RELEASE.md entries in both crates (zerover: breaking = minor) and 100% line coverage with deterministic tests — history shows timing/randomness paths are deliberately refactored to be deterministically testable rather than nocov'd.
