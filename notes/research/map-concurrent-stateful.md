# Code map: concurrent-stateful

> Research notes compiled 2026-09-02 at commit a0185a65 (branch base, == main at the time).
> References are `path:line` at that commit. Part of the nondeterminism design notes; see `../design.md`.

SUMMARY: Concurrent stateful testing (PR #378, merged 2026-08-20, building on test-case clones from PRs #359/#360, 2026-07) lets a user write `#[hegel::concurrent_state_machine]` + `stateful::run_concurrent(m, tc, min, max)`; the engine draws a concurrency level, the frontend spawns that many worker threads, and each worker draws from its own cloned choice stream while a shared engine-side machine hands out rules per round/group. Requesting `max_concurrency > 1` flips the whole run into a sticky "nondeterministic" mode: the first such case is rejected like a failed assumption, every later case is stamped nondeterministic up front, and the engine then skips data-tree recording (and novel-prefix generation and the choice-tree mismatch check), span mutation, targeting, verify+shrink, database persistence/reuse, and reproduce blobs — failures are reported once, from the discovering execution, via a frontend-side stash. There is no user-facing setting: an earlier `nondeterminism` setting was removed (commit 5c7456b2) in favor of the engine deriving the flag from machine creation.

## User-facing API: defining a concurrent machine
`#[hegel::concurrent_state_machine]` on an impl block (re-exported at src/lib.rs:594, expanded by hegel_macros::stateful::expand_concurrent_state_machine) generates a `ConcurrentStateMachine` impl with `rules() -> Vec<ConcurrentRule<Self>>` (fn(&M, TestCase) — shared &self, mutable state needs interior mutability; the macro rejects &mut self receivers) and `invariants() -> Vec<ConcurrentInvariant<Self>>`. Concurrency is expressed two ways: (1) `#[rule(group = "name")]` concurrency groups — rules in the same group may overlap, rules in different groups never do; bare `#[rule]`s share ANONYMOUS_GROUP (src/stateful.rs:162); (2) `run_concurrent(m, tc, min_concurrency, max_concurrency)` bounds the worker-thread count, drawn per test case weighted toward max (P_MAX_CONCURRENCY=0.75).
refs: src/stateful.rs:81-140, src/stateful.rs:162, src/stateful.rs:669-739, src/stateful.rs:966-1061, hegel-macros/src/stateful.rs:132-194, hegel-macros/src/lib.rs:126-136, src/lib.rs:531-594, hegel-c/src/native/core/state_machine.rs:38-62

## run_concurrent execution model (frontend)
run_concurrent registers the machine via `ctc.new_state_machine(rule_names, rule_groups, invariant_names, min, max)` which draws the concurrency level; spawns `concurrency` worker threads under std::thread::scope, each with a rounds mpsc::Receiver<TestCase> and events mpsc::Sender<WorkerEvent>. Main-thread loop: `machine_next_group(&tc, machine)` (root stream draws round stop decision + group), then sends `tc.clone()` (a fresh cloned stream per worker per round) to every worker, collects one WorkerEvent per worker (recv failure => WorkerEvent::Died), resolves the round (resolve_round: control payloads > overrun/invalid > panics, lowest worker index wins among panics; losing panics are noted as 'Dropped concurrent panic'), then runs sampled invariants on the main thread while workers are parked. Workers loop `machine_next_rule(tc, machine, worker_index)` until None; AssumeFailed inside a rule => machine_rule_rejected and continue; every unwind is caught in the worker and ferried as a typed event so no worker dies unreported.
refs: src/stateful.rs:966-1061, src/stateful.rs:761-807, src/stateful.rs:815-859, src/stateful.rs:881-900, src/stateful.rs:1076-1147, src/stateful.rs:537-579

## Engine-side machine: NativeStateMachine
Caller-owned handle (HegelStateMachine wraps Mutex<NativeStateMachine>; hegel-c/src/lib.rs:2509-2511 — 'concurrent use from two clone handles serializes'). ## Test-case clones: family/stream architecture (C ABI layer)
`hegel_test_case_clone` (hegel-c/src/lib.rs:1546-1591) creates a new HegelTestCase handle onto the same family: it calls src.stream.clone_stream() (DataSource method, backend.rs:119-128) and opens a deferred print slot in the parent's document region. FamilyShared (lib.rs:514-567) holds the root DataSource, an AtomicBool completed (compare_exchange — mark_complete runs exactly once family-wide regardless of which handle reports), and the family printer. Each handle has its own stream + its own Mutex<LocalState>; tc_guard returns HEGEL_E_CONCURRENT_USE if one handle is driven by two threads at once (lib.rs:1629-1649), but distinct clones draw concurrently. Frontend: TestCase is Send+!Sync; TestCase::clone calls handle.clone_handle() => hegel_test_case_clone (src/test_case.rs:289-298, src/ffi.rs:402-415); tc.child() shares the same handle (used for rule bodies), clone() forks a stream (used to hand work to threads).

## How interleaved draws are recorded: per-stream trees, not a merged sequence
There is NO cross-thread ordering or timestamp merging of draws. NativeTestCase is one *stream* with its own prefix, RNG, nodes, spans (state.rs:1552-1623). NativeTestCase::clone_stream (state.rs:1797-1857) records a single ChoiceKind::Clone node at the current position in the parent stream, spawns a child RNG (EngineRng::spawn), and gives the child its own node vec; on replay, a ChoiceValue::Clone prefix value at that position hands the child its recorded sub-stream (a non-clone value puns to an empty child). MAX_CLONE_DEPTH=100 (core/mod.rs:25). After the family concludes, reassemble() (state.rs:1867-1883) recursively freezes each child and replaces the placeholder clone node with a RealizedStream (nodes+spans+span_events), producing one self-contained *tree-shaped* choice sequence. Determinism claim: clone identity (parent's clone_counter) is deterministic because a handle is only cloned from its owning thread, so where a clone anchors is schedule-independent; only the values *within* each stream are replayed, not the cross-stream interleaving of the user's side effects. Family-wide shared state: conclusion, draw budget (total_draws/budget atomics), target observations, events, fresh ids, generation (swarm) parameters (state.rs:1372-1429).
refs: hegel-c/src/native/core/state.rs:1552-1623, hegel-c/src/native/core/state.rs:1797-1857, hegel-c/src/native/core/state.rs:1867-1883, hegel-c/src/native/core/state.rs:1362-1429, hegel-c/src/native/core/choices.rs:690-720, hegel-c/src/native/core/choices.rs:722-900, hegel-c/src/native/core/mod.rs:19-25

## Deterministic multi-thread generation exists independently of the concurrent-machine feature
Plain `tc.clone()` + move-to-thread is documented as *fully deterministic*: same seed replays the same values on every stream, failures shrink normally (src/test_case.rs:196-246). The docs explicitly scope the guarantee: 'Determinism extends exactly as far as your own code's determinism' — races on user state (e.g. which clone consumes from a shared queue, or shared pools/collections used from two threads at once) make outcomes schedule-dependent even though each stream's values replay faithfully. So the clone machinery itself does NOT trigger nondeterministic mode; only `new_state_machine` with max_concurrency>1 does. ConcurrentPool draws are made atomic engine-side (empty-check/selection/consumption under with_ntc), accepting that a shared pool couples workers' streams 'in a nondeterministic run … nothing downstream depends on that independence anyway' (src/stateful.rs:346-354).
refs: src/test_case.rs:196-255, src/stateful.rs:335-491, hegel-c/src/native/data_source.rs:375-403, hegel-c/src/lib.rs:1554-1560

## Worker output attribution and print regions
Workers' notes/draw lines are stamped '[worker N +X.XXXms] ' via a WORKER_INDEX thread-local set in worker_loop (src/stateful.rs:164-177, 890) and read by TestCase::worker_line_prefix against the family-shared case_start Instant (src/test_case.rs:871-881, 121-125). Each per-round TestCase clone anchors its print region in the parent document at clone time, so the final document groups each round's output worker-by-worker deterministically by anchor position, however threads were scheduled (hegel-c/src/lib.rs:592-598; commits c97ef40c, eb76aeeb, b64dbece). The buffered lines are what NondetStash replays as the failure report.

## Worker-event classification and panic-precedence policy
resolve_round precedence: control payloads (InternalError/InvalidArgument/LoopDone, plus synthesized Died) win over overrun/invalid, which win over panics — rationale documented: a panic co-occurring with an engine-side family conclusion is untrustworthy because the concluding draw abandoned a rule mid-execution (canonically poisoning a model lock) and can induce panics no real schedule could produce; a dropped genuine panic merely resurfaces later, while a reported fake panic is a false bug. Among panics, lowest worker index wins; dropped panics are noted into the case's output buffer. Overrun => raise StopTest; invalid => raise AssumeFailed on the main thread.
refs: src/stateful.rs:1063-1147, src/stateful.rs:761-807

RELEVANCE: This feature is the existing prior art for nondeterministic tests, and it handles them by wholesale surrender rather than accommodation: a single sticky Engine::nondeterministic bool (test_runner.rs:998) disables every determinism-dependent subsystem at its call site (data tree, novel prefixes, mismatch check, span mutation, targeting, verify+shrink, database, blobs), so any new design gets one all-or-nothing flag as its starting hook, with the disable points already enumerated and individually gated. Key structural constraints for a design discussion: (1) nondeterminism is currently *declared* (max_concurrency>1 at machine creation), never *detected* — the choice-tree mismatch check that could detect divergence is itself turned off once the flag is set, and the flag can only ever go false->true; (2) the flag's granularity is the whole run, not a test case or a subtree — one concurrent machine anywhere poisons replay/shrinking for everything; (3) the first declaring case is sacrificed (rejected as invalid via reject_concurrent_machine) purely so later cases can be stamped before they start, because the frontend must decide capture-at-discovery (run_lifecycle.rs:288) before running the body — any incremental detection scheme faces the same 'too late to capture this case' problem; (4) failure reporting in this mode relies on a frontend NondetStash that can silently lose to an engine-side family conclusion, and at most one failure per run is reported; (5) the clone/family/stream machinery is the strongest deterministic foundation available: per-thread draws are already recorded as an interleaving-free tree (Clone nodes + reassemble), replay of *values* is schedule-independent, and the engine assumes clone anchors are deterministic because handles are cloned only from their owning thread — a design that shrinks nondeterministic tests could build on replaying these per-stream sequences while treating pass/fail outcome divergence (currently RunError::Flaky / RunError::NonDeterministic hard errors at test_runner.rs:247,304,373,539,544) as expected rather than fatal; (6) determinism assumptions are baked into RunError semantics: Flaky and NonDeterministic are run-aborting errors everywhere the flag is off, so 'sometimes fails' currently has no representation other than run failure.
